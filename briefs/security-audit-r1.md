## Findings, highest severity first

### S1 — HIGH — Shared-shard message and thread primary keys allow one mailbox sync to overwrite another mailbox's cache

**Locations:** `lib/db/schema.ts:956` (`messages.id` global primary key), `lib/messageIds.ts:26` (account-independent RFC Message-ID hash), `lib/db/messages/upsert.ts:143` (existing-row lookup scoped only to the syncing account), `lib/db/messages/upsert.ts:183` (global INSERT OR REPLACE), `lib/db/messages/upsert.ts:194` (FTS deletion by row ID), `lib/db/schema.ts:1046` (`threads.threadId` global primary key), `lib/db/threads.ts:294` (thread replacement). The watcher reaches these writes via its sync job; the same store is used by cross-account copy ingestion.

**Boundary and scenario:** Mailboxes A and B are configured to share a physical shard, which the design explicitly permits. A remote sender or a compromised B IMAP server supplies a Message-ID already present in A. The ID builder returns the same row ID for both accounts. The B-scoped collision lookup sees no B row; INSERT OR REPLACE then replaces A's globally keyed row with B's row and replaces its FTS data. Even distinct messages with the same conversation root collide in the globally keyed thread index. A common message delivered to both mailboxes causes this without an attacker. A malicious sender who knows an existing Message-ID can deliberately trigger it through B, without A membership.

**Reproduction:** `security-audit-r1-probes/integration.test.ts`, tests:

- `FINDING S1 shared shard same RFC Message-ID sync overwrites another account message and FTS`: maps both synthetic accounts to one dbPath, inserts A, syncs B using the real ID builder and upsert API; A's row becomes unavailable, B contains its replacement, A's FTS hit disappears.
- `FINDING S1 shared shard distinct messages with common thread evict other account thread index`: A's message remains, but syncing B with the same thread ID removes A's thread index and A's thread listing becomes empty.

The fixture's master dbPath update establishes the supported storage topology; it is not claimed to be an attacker-writable configuration field. No canonical IMAP deletion or plaintext cross-mailbox body disclosure was demonstrated. Impact is unauthorized integrity/availability loss of another mailbox's local cache/index, potentially recurring whenever either account syncs.

**Fix:** Enforce account identity in every durable key, including message, thread, FTS linkage and dependent foreign keys, or introduce an account-namespaced internal message key and a composite `(accountId,threadId)` thread key with a migration. Preserve the external RFC Message-ID separately. Replace broad REPLACE behavior with conflict updates scoped to the complete key. Check existing shared files for prior collisions; a migration cannot recover already overwritten rows without resync. Exercise the same message and shared roots through watcher sync, full/repair/resync, copy ingestion, attachments, translations and topic/remap paths. A temporary safe operational constraint is rejecting shared shard mappings at startup, pending that migration.

**Later slices:** UI/identity changes alone do not repair this. Re-evaluate any final schema migrations, collision logic and summary joins.

### S2 — MEDIUM — Attachment preview discloses another mailbox's filename through a shared shard

**Locations:** `lib/db/messages/retrieval.ts:159`–163; `app/api/accounts/[accountId]/messages/[messageId]/attachments/[attachmentId]/route.ts:70` (metadata lookup), `:93` (filename in preview title).

**Boundary and scenario:** A viewer of mailbox A supplies a message-row ID and attachment ID belonging to inaccessible B. The route authorizes A, then getAttachmentMeta opens their common shard and selects by messageId/attachmentId without joining messages.accountId. `?preview=1` returns HTML containing B's filename before checking any A-scoped source/data file. IDs may be learned externally or guessed from deterministic attachment naming; possession of an ID is not mailbox authorization.

**Reproduction:** `integration.test.ts`, `FINDING S2 attachment preview discloses another mailbox filename in shared shard`: the real viewer cookie has A membership only; A's getMessageById for B's row is null; the A-addressed HTTP preview returns 200 and `private-project-B.pdf`. The probe also checks that A-scoped attachment bytes are absent. **Full attachment-byte disclosure was not demonstrated**; disk paths remain account separated.

**Fix:** Join attachment metadata to its owning message and require `messages.accountId = accountId`, and verify ownership before preview, ETag or content handling. Apply the same invariant to getAttachmentIds and removal/cache helpers; those omissions are source candidates, not separately reproduced HTTP exploits. The correct result for this probe is 404 with no filename. Preserve authorization on 304 responses.

**Later slices:** Final attachment/UI previews need the same boundary; membership DTO fixes do not fix this query.

### S3 — MEDIUM — HTML mail permits automatic remote loads and refresh navigation

**Locations:** `lib/html/sanitize.ts:57`, `:65`–75; `app/components/HtmlMessage.tsx:699`, `:719`; `app/api/accounts/[accountId]/messages/[messageId]/html/route.ts:95`–100; `next.config.ts:14`.

**Boundary and scenario:** An external mail sender controls HTML later displayed by an authenticated household member. The sanitizer retains HTTP(S) image/srcset URLs, unrestricted inline CSS and style blocks (including external @import), and meta http-equiv/content, including refresh. The regular viewer writes sanitized HTML into a same-origin srcdoc iframe with no sandbox. The standalone HTML route returns retained remote image/import/refresh markup without a response CSP. Thus the tailnet is not an egress/privacy boundary for mail viewing: normal HTML interpretation can report the message-open identifier and reader IP to a sender; opening the standalone HTML view can also navigate to an external phishing page. The source comment excluding external link stylesheets explicitly recognizes the tracking risk, but @import still survives.

**Reproduction:** `integration.test.ts`, `FINDING S3 HTML display retains remote pixels, CSS import and meta navigation without response CSP`: a synthetic HTML email goes through the real authenticated HTML route; its pixel URL, @import and meta refresh survive; response CSP is absent; the component source has no iframe sandbox. `<script>`, onerror and form elements from the same input are removed. Evidence establishes the delivered active-resource/navigation markup. The resulting network/navigation behavior follows standard browser semantics; no external tracker was contacted and no browser exploit or arbitrary script execution was demonstrated. This is a privacy/navigation finding, **not a proven stored-XSS finding**. Normal iframe construction extracts body/style content, so the meta-refresh observation applies specifically to the standalone HTML route; remote images/styles apply to both rendering paths.

**Fix:** Default to blocking remote image/srcset/CSS resources until the user explicitly allows them; sanitize CSS imports and URL-bearing properties, remove refresh and other active http-equiv directives. Add a viewer sandbox allowing only the minimum needed capabilities, with scripts/forms/top-navigation excluded; retain same-origin access only if required by the sizing implementation. Apply a matching restrictive CSP to standalone mail HTML and explicit no-referrer policy. Restrict remote resources without breaking local CID attachment URLs. Recheck browser behavior for both inline and standalone viewing.

**Later slices:** Re-run against final reading/compose/identity and attachment preview flows. A changed UI shell alone does not establish safe mail rendering.

## Hypotheses and exact validation gaps

These are not confirmed findings and carry no severity.

- **NV1 — Oversized or malformed full IMAP sources may exhaust the shared process/worker.** `lib/mail/imap/sync.ts:902`, `:1118` request full `source:true`; streaming part helpers have 1 MiB/5 MiB caps, but there is no demonstrated aggregate raw-message budget on these full-source paths. Worker count/backoff does not bound one literal. No hostile-size/deep-MIME stress fixture was run. Validate in an isolated fixture using modest increasing bounded literals, byte/parse-depth limits, cancellation, memory ceilings and no household mailbox. Do not infer a service-wide DoS from the source pattern alone.
- **NV2 — Effective proxy boundary and global browser headers are unverified.** `next.config.ts:14` only configures reset-page headers; no global CSP/frame-ancestors/referrer-policy is set there. The TLS proxy could add them. No deployed clickjacking or proxy-header bypass was reproduced. Require a loopback-only/otherwise firewalled Next listener, proxy overwrite of forwarded headers, canonical public origin and exact RP ID; inspect effective headers and trusted-IP topology locally before exposure. Better Auth's IP resolver is distinct from Noctua's TRUSTED_PROXY_HOPS resolver: without explicit library trustedProxies it accepts a single valid XFF value and rejects a chain, falling back to a shared per-path bucket. That can cause cross-user throttling, not a demonstrated spoofing bypass in this configured deployment.
- **NV3 — Data-dir/backup filesystem protection and consistency are operator obligations not yet validated.** `lib/db/connection.ts:87`, `lib/storage.ts:70` create directories/files without imposing a service-wide restrictive umask. Lifetime-lock mode is separately verified. No host filesystem permissions, keys or real backup were inspected. Validate service ownership, umask/data-dir 0700 policy, read access to master/shards/source/attachments, independent key custody and the §11 quiesced restore contract. A copied data directory exposes cached mail, comments, recipients, metadata/audit/preferences, auth password hashes and live session-token material; IMAP passwords and Better Auth factor secrets depend on their respective external keys. MCP tokens are hashed. Encryption of credentials is not encryption of all mail or of a backup. Key independence is documented but startup does not compare IMAP_SECRET_KEY to BETTER_AUTH_SECRET; decodeSecret also accepts legacy plaintext rows. Validate migration and backups instead of claiming the entire datastore is cryptographically protected.
- **NV4 — Enumeration/timing across pending/banned login branches needs final-mount validation.** `lib/authPolicyHandler.ts:91`–105 reserves a known user's security slot before password verification; `lib/db/authPolicy.ts:335`, `:362` can reject on ban or pending operation earlier than the stock equalized unknown-user path. No statistical timing/parallel enumeration probe was preserved, and public /api/ba currently returns 503. Compare status/code/body/timing for unknown, wrong-password, banned and in-progress users after activation, without weakening the transactional slot barrier. No enumeration exploit is asserted here.

### B — Shared-shard data isolation (5)

1. Collaboration scalar/batch state, thread existence, comments and activity queries are account scoped for two accounts sharing one physical dbPath. Cross-account comment IDs do not edit/delete A through B. Evidence: B1 and the SQL trace in lib/db/threadCollab.ts.

4. Watcher unread summaries count each account's own nondeleted INBOX messages and states. Evidence: B3, lib/db/mailboxSummary tests and selected-account summary tests.

Successful copied-message collision in shared storage remains S1; no successful shared-shard copy authorization bypass is claimed.

### C — Watcher trust boundary (5)

1. Watcher startup requires exact opt-in `NOCTUA_MAILBOX_WATCHER=1` and supported DB storage. Evidence: 12 gate cases; instrumentation awaits getAuth before watcher startup (source).
2. Worker leases/admission and scheduler ownership are in the master DB, not controlled by mailbox shard tables; one live owner is not displaced on a late heartbeat. Evidence: processLeases source and four executed multiprocess tests covering capacity, orphan recovery, confirmed-exit failure, bounded watcher admission and cleanup retries.
3. UIDVALIDITY changes clear old namespace watermarks before the new state is saved. The SSE path checks validity before its equal-UIDNEXT early return. Evidence: db.mailboxState tests and source trace. This is not a full malicious-server UID reset fixture.

Watcher state logs and mailbox event producers use account IDs/state, not subjects/passwords; events are not directly broadcast to arbitrary users in this stand. subscribeMailboxEvents has no final cross-account user-event consumer yet. ### E — Secrets and storage (5)

3. Credential/lifecycle/recovery audits in the tested success/fault paths contain actor and changed-field metadata rather than submitted passwords, TOTP seeds or reset/invite/bearer capabilities. Evidence: the baseline 142-test run and teamAuthSlice3 audit-failure tests.

5. Unsafe cookie storage, desktop=true, noncanonical/insecure production origin, wildcard origins, RP mismatch and telemetry enablement are rejected; missing IMAP key fails on startup/use. Evidence: E2, secret and betterAuth tests. Independent IMAP/auth keys and backup restore are not runtime-enforced/validated claims (NV3).

3. Noctua credential-proof wrappers count user and IP before expensive proof work (five/minute), with purpose/session/generation bound, one-use grants; IMAP proof has its separate personal-identity budget. Evidence: authSecurity/imapLoginPolicy source, baseline and authPolicyFlows grant/CAS tests. Production proxy topology remains NV2.
4. Signup/recovery/admin wrappers enforce their separate attempt budgets: signup and recovery three/minute; admin actor ten/minute and IP thirty/minute span actions/module graphs. Evidence: baseline 142-test run, including throttled-valid-reset preservation and secret-free issuance. Ordinary MCP token minting has no separate burst/quota limiter in its route; only MFA/current editor membership, label/TTL validation and authenticated storage access were established. No arbitrary passkey-endpoint rate-test or statistical timing-enumeration result is claimed.
