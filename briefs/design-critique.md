

# LENS: security

## Verdict
The design is directionally right (membership-based guard, hashed app passwords, MCP role re-check, admin least privilege) but it is not safe to implement as written. Three things must change before coding starts: (1) the "unchanged" legacy IMAP fallback in §4.2 step 4 is a full account-takeover path because today's login resolves the session user to `account.ownerUserId` / first linked user (app/api/auth/login/route.ts:64-69), so anyone who knows a shared mailbox's IMAP password is issued the owner's identity and, under D4, access to every mailbox the owner has — regardless of the owner's app password; (2) there is no revocation primitive at all: `disabledAt`, password change and admin reset only affect future logins, while the stateless cookie is rotated indefinitely by `/api/auth/me` and MCP tokens stay valid, so "disable user" is a no-op against an active attacker; (3) `POST /api/accounts` (app/api/accounts/route.ts:27-39 + lib/db/users.ts:67-75 `INSERT OR REPLACE`) lets any viewer re-attach the active mailbox, overwrite its IMAP host and reset their own `user_accounts.role` to the default `manager`. Add an `iat`/`passwordUpdatedAt`/`disabledAt` check to every guard, rewrite the legacy path to only ever issue the typed email's own user, and make all membership writes role-preserving and manager/admin-gated. The remaining issues (default `both` storage mode breaking MCP minting and D2's isolation claim, forgeable sessions without `SESSION_SEAL_KEY`, account `email`/host patching enabling credential harvesting, manager/admin member-API mismatch, unique index migration crash) are fixable in the design text but should be settled before the `feat/team-auth` branch begins.

## Issues

### [BLOCKER] §4.2 step 4 / D3 — Legacy IMAP fallback issues the session as the mailbox owner, bypassing the owner's app password
**Problem:** The doc says the legacy flow runs 'unchanged' whenever the typed email has no user row or a user without a hash. Today's flow (app/api/auth/login/route.ts:36-39) resolves the account by `accounts.email`, then `accounts.imap.user`, then any linked account, and then (lines 64-69) sets `resolvedUserId = account.ownerUserId ?? linkedUserIds[0] ?? emailUser?.id ?? account.id`. Scenario A: shared mailbox support@example.com is owned by user U (u@example.com, has passwordHash, role admin). Attacker who knows the mailbox IMAP password POSTs `{email:'support@example.com', password:<imap pw>}`. `getUserAuthByEmail('support@example.com')` finds no user → legacy path → account found by email → IMAP verify OK → session `{userId: U.id, role:'admin'}`. Under D4 the attacker now has manager rights on every mailbox U owns plus `/api/admin/*`. Scenario B: legacy viewer V (no hash) is a member of the same mailbox and logs in with their own email: no `accounts.email` match, linked-account match → same mailbox → session issued as U, not V. Scenario C: admin-created mailbox (`ownerUserId = null`) → `linkedUserIds[0]`, i.e. whichever member sorts first. The password-login branch in §4.2 step 3 does not protect any of these because the branch is selected by the typed email, not by the user that ends up in the session.

**Fix:** Rewrite step 4 instead of keeping it 'unchanged': (a) the legacy path is only entered when `getUserAuthByEmail(email)` returns a user with `passwordHash IS NULL` and `disabledAt IS NULL`, or when the users table is empty (bootstrap); (b) the account to verify against must be one of `listAccessibleAccountsForUser(thatUser.id)` whose `email` or `imap.user` equals the typed email — never an arbitrary account matched by `accounts.email`/`imap.user`; (c) the session `userId` is always `thatUser.id`; delete the `ownerUserId`/`linkedUserIds[0]`/`account.id` fallbacks; (d) refuse legacy login for accounts with `ownerUserId = null` or more than one member (shared mailboxes require app passwords); (e) only write the password back to the account row when `thatUser` is the owner/manager. Add tests for scenarios A-C in §10.

### [BLOCKER] §4.4 / §4.5 / §5.2 MCP — Disable, password change and admin reset do not invalidate existing sessions or MCP tokens
**Problem:** Sessions are stateless sealed cookies (lib/auth.ts:57-73) with no server-side state; `/api/auth/me` re-seals the cookie on every poll with a fresh `exp` (app/api/auth/me/route.ts:29-38), so an open tab keeps a session alive indefinitely. `disabledAt` is only consulted at login (§4.2 step 5). `requireMcpAccountContext` (lib/auth.ts:300-309) only checks the token row and expiry; the doc adds a membership re-check, but disabling a user does not remove memberships. Scenario: admin disables user X after discovering their laptop was stolen. The thief's browser session continues to pass `requireAccountContext` (membership still present), continues to pass `requireAdminSessionOr403` if X was admin (app/api/admin/_auth.ts:8-9 checks role, not disabledAt), and X's MCP tokens (which can have `exp = 253402300799`, lib/auth.ts:11) keep working. Likewise after a password change or admin reset the old cookie stays valid for the full sliding TTL, so a compromised session cannot be evicted.

**Fix:** Add `iat: number` to `SessionData` and `McpSessionData`. Introduce an async `requireActiveUserSession(request)` (used by `requireAccountContext`, `requireAdminSessionOr403`, `/api/auth/me`, `/api/auth/password`, `/api/auth/switch-account`) that loads `{disabledAt, passwordUpdatedAt}` for `session.userId` and returns 401 when `disabledAt != null`, when the user row is missing, or when `iat < passwordUpdatedAt`. `requireMcpAccountContext` additionally rejects when `createdByUserId` is disabled/missing; admin `PATCH {disabled:true}` and `DELETE user` also delete that user's `mcp_tokens`. `POST /api/auth/password` must re-issue the cookie with a new `iat` after updating `passwordUpdatedAt` so the caller's own session survives. Cover 'disabled user with live cookie' and 'live MCP token after disable' in §10.

### [BLOCKER] §5.1 / §5.2 (`accounts/route.ts`) — POST /api/accounts lets a viewer re-attach the active mailbox, overwrite its IMAP host and self-promote to manager
**Problem:** app/api/accounts/route.ts:27-39: if `accountIdFromEmail(payload.email)` already exists it only calls `requireSessionAccountOr403` (active account match), then `upsertAccount({...payload, ownerUserId: existing.ownerUserId})` and `addUserAccountLink(session.userId, accountId)`. `addUserAccountLink` is `INSERT OR REPLACE INTO user_accounts (userId, accountId)` (lib/db/users.ts:70), which after the §3.1 migration rewrites the row with `role = DEFAULT 'manager'`. Scenario: viewer V (active mailbox S) POSTs `{email: S.email, name:'x', imap:{host:'imap.attacker.example', port:993, secure:true, user:S.imap.user, password:'anything'}, smtp:{...}}`. Result: V's membership row becomes `manager`; S's IMAP host now points at the attacker; the next sync worker decrypts the stored password and sends it to the attacker host. §5.1 lists `accounts/route.ts` as 'move to requireAccountContext with the role from §5.2' but §5.2 has no row for attaching an existing account, so the implementer has no instruction to gate it.

**Fix:** In §5.2 add a row 'Attach/overwrite an existing account via POST /api/accounts: manager'. In §3.1 rules require that `upsertUserAccountLink` never downgrades or resets an existing role implicitly: implement as `INSERT INTO user_accounts(userId, accountId, role, grantedByUserId, grantedAt) VALUES (...) ON CONFLICT(userId, accountId) DO NOTHING` for the self-link path, and a separate explicit `setUserAccountRole` used only by admin/manager member endpoints. Replace the remaining `INSERT OR REPLACE` in `addUserAccountLink` (lib/db/users.ts:70) and extend `saveUserAccounts` to carry `role` so legacy callers do not reset roles to manager.

### [MAJOR] §2 D2 / §5.1 step 3 / §5.2 MCP tokens — Default IMAP_CREDENTIALS_STORAGE=both defeats D2's isolation claim and breaks MCP token minting for password sessions
**Problem:** lib/secret.ts:4-8: default mode is `both`, where `shouldStorePasswordInDb()` and `shouldIncludeSessionCredentials()` are both true. §5.1 step 3 and §8 only special-case cookie-only mode, so in the default config shared mailboxes and password login are allowed, but: (1) `buildMcpSessionPayload` (lib/auth.ts:225-232) throws 'Current session does not include IMAP/SMTP credentials' whenever `shouldIncludeSessionCredentials()` is true and the session has no creds — every password-login editor/manager gets a 400 from `POST .../mcp-tokens` in the default deployment; (2) legacy-login users in `both` mode still carry creds in their cookie, and `requireSessionOr401` → `cacheSessionCredentials` (lib/auth.ts:139, lib/credentials.ts:14-20) overlays them into the process-global per-account cache that every `getAccountById` applies (lib/db/accounts.ts:74), so whichever legacy user last made a request supplies the IMAP identity used for password-login users' IMAP operations on that mailbox — exactly the hazard D2 says is avoided by 'requiring db'.

**Fix:** Define a single predicate `teamFeaturesSupported() = shouldStorePasswordInDb() && !shouldIncludeSessionCredentials()` (i.e. mode must be exactly `db`) and use it for: password login (401 + startup warning otherwise), signup with app password, admin mailbox creation, member grants, and §5.1 step 3 (require `session.accountId === accountId` whenever it is false). Change `buildMcpSessionPayload` to embed credentials only when `shouldIncludeSessionCredentials() && !shouldStorePasswordInDb()`; otherwise rely on the DB row. Document in §8 that `both` is treated like `cookie` for team features, and change the documented default in deployment docs to `db`.

### [MAJOR] §4.1 / §4.6 — Sessions are forgeable when SESSION_SEAL_KEY is unset; with membership-based authz that is total compromise
**Problem:** lib/auth.ts:8 and :45 fall back to the literal key `dev-session-key` when `SESSION_SEAL_KEY` is empty, and instrumentation.ts:9-10 only asserts `IMAP_SECRET_KEY`. Today a forged cookie still needed valid IMAP creds in cookie mode; under this design (db mode, no creds in cookie, all authorization derived from `session.userId`) anyone can seal `{userId:<admin id>, exp:...}` with the public default key and obtain admin and every membership. User ids are UUIDs but are exposed to every viewer through `GET .../members` (§5.4) and `thread_activity.actorUserId`.

**Fix:** In §4.6 add: `assertSessionSealKeyConfigured()` in `instrumentation.ts` that refuses to start (or at minimum refuses password login and admin routes) when `SESSION_SEAL_KEY` is shorter than 32 bytes and `NOCTUA_DESKTOP_MODE !== 'true'`; in desktop mode generate and persist a random key under `NOCTUA_DATA_DIR` instead of using the fixed fallback. Mention the key in `doc/AUTHENTICATION.md` as hard-required.

### [MAJOR] §5.3 — Managers can patch `email` and IMAP/SMTP host/user without re-verification, enabling credential harvesting and id/email mismatch
**Problem:** `mergeAccount` (lib/db/rowParsers.ts:142-156) spreads `...payload` and nested `imap`/`smtp`; §5.3 only blacklists `id`, `ownerUserId`, `dbPath`. (1) `accounts.id` is `accountIdFromEmail(email)` (signup:72, accounts POST:26); patching `email` breaks that invariant and makes a later `POST /api/accounts` with the new email create a second account for the same mailbox. (2) Legacy login matches `accounts.email`/`imap.user` (login/route.ts:36-39) across all accounts: a manager of mailbox S sets `S.email = 'victim@example.com'` and `S.imap.host = 'imap.attacker.example'` (a server accepting any password); when legacy user victim@ next logs in, the typed password is sent to the attacker and, with today's resolution, the victim is issued S's owner identity. (3) Even without the login angle, any manager can redirect `imap.host` so the sync worker (lib/syncOperation.ts:254) decrypts and submits the stored password set by another manager to a host of their choosing, with no re-entry of the secret.

**Fix:** Extend §5.3: `email` is immutable via PUT (changing the mailbox address means creating a new account). Any change to `imap.host|port|secure|user` or `smtp.host|port|secure|user` must go through the relogin-style path: require the password in the same request and call `verifyImapCredentials` against the new endpoint before persisting; reject host/user changes without a password with 400. Combine with the legacy-login fix so login never resolves an account by `accounts.email`/`imap.user` that the typed user is not a member of.

### [MAJOR] §2 D5 / §4.4 / §5.4 — D5's 'admin cannot read mail / honest audit trail' does not hold: admin reset + self-grant leave no trace and allow impersonation
**Problem:** D5 justifies admin-without-mail-access with the audit trail, but: (a) `POST /api/admin/users/[userId]/password {generate:true}` returns a plaintext password the admin then knows permanently; nothing forces the user to rotate it, so the admin can log in as any manager and every `thread_activity` row is attributed to that manager; (b) `PUT /api/admin/accounts/[id]/members/<adminId> {role:'manager'}` followed by `DELETE` of the same membership leaves nothing behind — `grantedByUserId` lives on the row that was just deleted; (c) `POST /api/admin/users {email, password}` likewise creates a user whose password the admin knows. There is no master-DB audit table in §3.1, and `thread_activity` is per thread in the shard.

**Fix:** Either drop the audit-trail rationale from D5, or add: `users.mustChangePassword INTEGER` set by admin reset/create and enforced by `requireActiveUserSession` (only `/api/auth/password` and `/api/auth/me` allowed until cleared); invalidate sessions on reset via the `iat` check; and a master-DB `admin_audit(id, actorUserId, action, targetUserId, targetAccountId, payload, createdAt)` table written by every `/api/admin/*` mutation (user create/role/disable/delete, password reset, member grant/revoke including self-grant, mailbox create). Expose it read-only in the Admin panel.

### [MAJOR] §5.2 / §5.4 / §7.5 — Members tab is 'manager' in §7.5 but only admin member endpoints exist; and any manager can delete the shared mailbox
**Problem:** §7.5 lists 'Members (manager)' and §5.3 says `shared` is derived from member count, but §5.4 defines membership PUT/DELETE only under `/api/admin/...` behind `requireAdminSessionOr403`. Implementers of `feat/collab-ui` will either call admin routes from a manager session (403) or invent a manager route without escalation rules. Separately, §5.2 grants 'delete account' to `manager`; `DELETE /api/accounts/[accountId]` (app/api/accounts/[accountId]/route.ts:33-41 → `deleteAccountControlPlane`, lib/db/accounts.ts:122-148) removes all memberships and MCP tokens and can delete the shard file holding every member's comments and activity. A non-owner manager (e.g. a contractor granted manager by an admin) can destroy a mailbox shared by the whole team.

**Fix:** Decide and write down: (option 1) managers may manage members via `PUT/DELETE /api/accounts/[accountId]/members/[userId]` with `requireAccountContext(minRole:'manager')` and explicit rules — cannot modify or remove the owner, cannot change own role, cannot remove self if last manager, may grant at most `manager`; the admin routes stay as the override; or (option 2) the tab is admin-only and §7.5 is corrected. Restrict `DELETE /api/accounts/[accountId]` (and `PUT` of `ownerUserId` via admin) to the owner or an admin; non-owner managers get 403 with 'Only the owner can delete this mailbox'.

### [MAJOR] §3.1 — `CREATE UNIQUE INDEX ... ON users(lower(email))` crashes startup on existing installs with case-variant duplicates
**Problem:** Today signup stores `account.email` as typed (app/api/auth/signup/route.ts:114) while `users.email` is only case-sensitively UNIQUE (lib/db/schema.ts:606-611), so an existing install can legitimately hold `Alice@Example.com` and `alice@example.com`. `initMasterSchema` runs from `instrumentation.ts`; the unique index creation throws, the server never starts, and the operator has no UI to fix it.

**Fix:** In §3.1 rules: before creating the index, `UPDATE users SET email = lower(trim(email))`, then detect duplicates with `SELECT lower(email) FROM users GROUP BY 1 HAVING count(*) > 1`; if any exist, log them with their ids, create a non-unique index instead, and enforce uniqueness in `insertUser`/`POST /api/admin/users` (409) until the admin resolves them. Add a migration test with pre-seeded duplicates.

### [MAJOR] §4.3 — Signup claims the invite before checking email uniqueness and outside a transaction, burning invites and leaving partial state
**Problem:** Today `claimInviteCode` (signup/route.ts:97-103, atomic UPDATE in lib/db/inviteCodes.ts:85-101) runs before the user insert; the doc keeps 'same precheck + atomic claim as today' and adds a 409 for duplicate email, but a duplicate-email insert after the claim burns the single-use invite, and a failure in `upsertAccount` after `insertUser` leaves a user with a hash but no mailbox, no link and a consumed invite. The same ordering issue applies to the IMAP verify of the optional `account` (slow, failure-prone) if it is placed after the claim.

**Fix:** Order: validate payload and password policy → `getUserAuthByEmail` duplicate check (409) → verify IMAP for the optional account → hash password → single `db.transaction` that claims the invite, inserts the user, upserts the account and link (claim returns null → roll back and 400). Wrap in `withDbWriteRetry`.

### [MINOR] §4.2 step 4 vs §4.6 — Legacy path keeps 404 'Account not found' and 'Invalid IMAP credentials', contradicting the generic-401 rule and enabling mailbox enumeration
**Problem:** §4.6 says all auth failures return the same generic 401, but step 4 says the legacy flow is 'unchanged', and today it returns 404 for unknown accounts (login/route.ts:40-42) and a distinct 401 message for bad IMAP passwords (line 45). An attacker can therefore distinguish 'email belongs to a password user' (generic 401) from 'no such mailbox' (404) from 'mailbox exists, wrong IMAP password' (401 IMAP message).

**Fix:** State explicitly that the legacy branch returns the same `401 { ok:false, message:'Invalid email or password' }` for unknown account, failed IMAP verification and disabled user, and that the 400 'Missing credentials' is the only other response. Add an enumeration test to §10.

### [MINOR] §4.4 — No rate limit or length cap on password endpoints
**Problem:** `POST /api/auth/password` verifies `currentPassword` with argon2id but has no limiter (login uses `createRateLimiter` 5/min per IP, lib/rateLimit.ts:28-58). With a stolen cookie an attacker can make unlimited online guesses of the current password and then lock the victim out by setting a new one; each guess also costs server CPU. `newPassword` has a minimum (10) but no maximum, so a multi-megabyte password turns argon2 hashing into a DoS vector.

**Fix:** Add a per-user limiter (`createRateLimiter({windowMs:60_000,max:5})` keyed by `session.userId`) to `POST /api/auth/password` and `POST /api/admin/users/[userId]/password`; cap passwords at 256 chars in `lib/passwords.ts` (400 above). With the `iat` mechanism, a successful change also evicts the attacker's session.

### [MINOR] §4.2 / §4.6 / §6.3 — No Origin/Content-Type check on JSON routes: login CSRF via text/plain forms and state-changing GETs under sameSite=lax
**Problem:** Routes call `request.json()` without checking `content-type` (login/route.ts:21, signup:35), and `Request.json()` parses any body, so a cross-site `<form enctype="text/plain">` can POST a JSON-shaped body to `/api/auth/login` and log the victim into an attacker-controlled account (login CSRF; `sameSite=lax` does not help because the response sets the cookie). `GET .../imap/poll` (app/api/accounts/[accountId]/imap/poll/route.ts:28) opens an IMAP connection on a GET that a cross-site top-level navigation can trigger with the lax cookie. The client already sends `X-Noctua-Client` on every request (MailClient.tsx:385-392), so a cheap preflight-forcing check is available.

**Fix:** Add a shared `requireJsonSameOrigin(request)` helper in `app/api/_helpers` that rejects mutating requests unless `content-type` starts with `application/json` and (`Sec-Fetch-Site` is `same-origin`/`none` or `Origin` matches the request host); apply it in the auth routes and all new POST/PATCH/PUT/DELETE routes in §4, §5.4, §6.3. Document in §4.6.

### [MINOR] §3.2 / §6.1 — Collaboration tables are keyed by threadId alone although accounts can share a shard dbPath
**Problem:** `thread_collab_state.threadId` is the sole PRIMARY KEY and the comment/activity indexes are `(threadId, createdAt)`; `accountId` is a plain column. `deleteAccountControlPlane` (lib/db/accounts.ts:131-136) explicitly handles accounts that share the same `dbPath`, so two mailboxes can live in one shard. Thread ids are Message-IDs, which are identical for a message delivered to two mailboxes (e.g. support@ and sales@ both CC'd). A viewer of mailbox B would then read, and an editor of B could delete, comments written by members of A. The `deleteThreadComment(accountId, threadId, commentId)` signature does not say the query must filter on all three.

**Fix:** Use `PRIMARY KEY (accountId, threadId)` for `thread_collab_state`, index comments/activity on `(accountId, threadId, createdAt)`, and state in §6.1 that every read/write filters `WHERE accountId = ? AND threadId = ?` (and `AND id = ?` for comment delete). Add a test with two accounts on one dbPath.

### [MINOR] §4.5 / §3.2 — Admin role patch, self-delete and attacker-controlled actorClientId are unvalidated
**Problem:** `PATCH /api/admin/users/[userId] {role}` does not say the value is validated; `mapUserRow` coerces anything non-'admin' to 'user' (lib/db/rowParsers.ts:38) but the raw string is still persisted. The self-protection covers demote/disable but not `DELETE` of oneself or demoting the last remaining admin (lockout; the startup admin invite is only minted when `users` is empty, lib/db/schema.ts:690-694). `thread_activity.actorClientId = 'web:<clientId>'` stores the raw `x-noctua-client` header, which any client can set to arbitrary length/content and which is rendered in the activity timeline.

**Fix:** Validate `role` against `['admin','user']` (400 otherwise); refuse `DELETE` of the calling admin and any change that would leave zero enabled admins (400); clamp `clientId` to e.g. 64 chars of `[A-Za-z0-9_-]` before storing it in activity rows (and in logs at lib/auth.ts:131).

## Missing
- A session revocation primitive: the design has no `iat`/`passwordUpdatedAt`/`disabledAt` enforcement in any guard, so 'disable user', 'change password' and 'admin reset' cannot evict an active attacker (stateless cookie + /api/auth/me sliding refresh + never-expiring MCP tokens).
- A master-DB admin audit log (who granted/revoked which membership incl. admin self-grants, password resets, role changes, mailbox creation); without it D5's 'honest audit trail' rationale is unsupported.
- Startup assertion for `SESSION_SEAL_KEY` (and a generated persistent key for desktop mode); under membership-based authz a forgeable cookie is full compromise.
- A rule for which storage mode supports team features: `both` (the current default) is neither excluded nor handled; define `db` as the only supported mode for password login/shared mailboxes and adjust `buildMcpSessionPayload` accordingly.
- Behaviour of `thread_collab_state.assigneeUserId`, comments and `assigned-to-me` filters when the assignee's membership is revoked, the user is disabled, or the user row is deleted (dangling ids are currently rendered via the members list, which will no longer contain them).
- Member-management rules for managers (if the §7.5 'Members (manager)' tab is kept): cannot touch owner, cannot change own role, cannot grant above manager, last-manager protection.
- Re-verification requirement when IMAP/SMTP host/user change on an existing account, and immutability of `accounts.email` (id derivation invariant).
- `mustChangePassword` after admin-set or admin-generated passwords, and invalidation of the user's other sessions on reset.
- Per-user (not only per-IP) rate limiting for the argon2 verification paths (`/api/auth/login` password branch keyed by lowercased email, `/api/auth/password` keyed by userId), plus a maximum password length.
- Same-origin / content-type enforcement for JSON mutating routes (login CSRF via text/plain forms is possible today and the design adds many new mutating routes).
- Email-normalisation migration for existing `users.email` rows and a duplicate-handling strategy before the `lower(email)` unique index is created.
- Transactional signup (invite claim + user insert + account upsert + link) and duplicate-email check before the invite is consumed.
- Handling of sessions whose `userId` is not a `users` row (today's `account.id` fallback at login/route.ts:69) in `POST /api/auth/password` and the new guards — they must be rejected, not treated as legacy users.


# LENS: data-integrity

## Verdict
The data model is the right shape (keying by threadId in the shard, additive DDL, no cross-DB FKs, EXISTS-based badge filters fit lib/db/messages/query.ts as written), and several asked-about points check out: `ALTER TABLE user_accounts ADD COLUMN role TEXT NOT NULL DEFAULT 'manager'` works (verified with bun:sqlite; SQLite only requires a non-NULL default); `getThreadCollabStates` needs no IN-chunking at 600 rows (40 000 bound parameters accepted; default limit is 32 766 since SQLite 3.32); the collab badges automatically bypass both unfiltered fast paths because they are gated on `badges.length === 0`, and every consumer of `where` (threadFilterSql, baseCount, invite-deck summary) uses alias `m`; initMasterSchema is not run concurrently by Next and its own worker children because instrumentation.ts initialises the master DB before any worker can be spawned. The design is NOT implementable as written in two areas, though. First, the thread remap/merge policy (§3.2) will throw inside the recompute transaction: `updates` in lib/db/threads.ts:425-437 holds per-message `{id, threadId, parentId}` rather than old→new pairs, one old thread can split or partially survive (unspecified), and the planned `UPDATE thread_topics SET threadId = new` / collab-state move collides on the primary keys (verified `UNIQUE constraint failed`), rolling back the whole recompute. Second, three data-integrity holes must be closed before branch 1 ships: the unique `lower(email)` index aborts `initMasterSchema` on existing case-duplicate users and, because `masterInitialized` is only set after success (lib/db/connection.ts:192-195), takes the whole app down; `addUserAccountLink`'s `INSERT OR REPLACE` silently resets an existing membership to `manager` once the role column exists and `POST /api/accounts` persists the raw client body via `upsertAccount`; and the "unchanged" legacy IMAP login resolves the mailbox owner's userId for any member, so every collaboration write by a not-yet-migrated user is attributed to the owner. Fix the remap specification, the migration guard, the link/POST write path, the mutation atomicity rules, and the legacy identity resolution first; the remaining items are smaller follow-ups. Repo root for all cited paths: /home/monkey/.t3/scratch/2026-10-22-https-github-com-paulwellnerbou-noctua-8f78a215/noctua-mail.

## Issues

### [BLOCKER] §3.2 rules / §6.1 remapThreadCollab — Remap policy is incomplete (split/partial threads) and the PK moves will throw inside the recompute transaction
**Problem:** `recomputeThreadIdsForAccount` (lib/db/threads.ts:399-449) builds `updates` as per-message `{ id, threadId, parentId }` (425-437); the old threadId exists only in `rows` (row.threadId) and is never paired with the new one, so the `remapThreadCollab(db, accountId, updates: {oldThreadId,newThreadId}[])` signature cannot be fed from it without extra derivation. The relation is not a function: with out-of-order arrival a message that was parked in thread <B> can move to <A> while other messages keep <B> (old id survives), or one old id can fan out to several new ids (split). The design only specifies many-old→one-new. Worse, the moves themselves fail: `thread_collab_state.threadId` is the PRIMARY KEY, and a typical merge (B into an A that already has a state row) or the planned `UPDATE thread_topics SET threadId = ? WHERE threadId = ?` (PK threadId+topicId, lib/db/schema.ts:858-864) raises `UNIQUE constraint failed` (verified with bun:sqlite). That exception is thrown inside the `db.transaction(() => {...})()` at threads.ts:443-446, so the messages UPDATE is rolled back too and the recompute worker (lib/workers/recomputeThreads.ts:12) exits 1 every time; thread recompute becomes permanently broken for any account where two merging threads share a topic or both have collab rows.

**Fix:** Specify the remap as: (1) derive pairs inside the existing transaction from `rows` (`row.threadId -> next.threadId` for rows where it changed) and group by old id; (2) after the messages UPDATE, if the old id still has non-deleted messages, leave its rows alone; if it maps to exactly one new id, move; if it split, follow the new thread that contains the message whose `messageId` equals the old id (root header), else the oldest message formerly in it, and record `anchorMessageId` accordingly; (3) for PK tables compute the merged row in JS (most recent updatedAt, not-closed wins, newest assignee, commentCount = COUNT of non-deleted comments after the move) and write it with `INSERT OR REPLACE` then `DELETE` the old ids; for thread_topics use `INSERT OR IGNORE INTO thread_topics SELECT ?, topicId, accountId, assignedAt FROM thread_topics WHERE threadId = ?` then `DELETE`; (4) `remapThreadCollab` must be synchronous (no await) because it runs inside the bun:sqlite transaction callback, and that transaction should be `db.transaction(fn).immediate()`; (5) add a test that merges two threads sharing a topic and two threads that both have state rows.

### [MAJOR] §3.1 DDL — CREATE UNIQUE INDEX ON users(lower(email)) aborts startup on existing case-duplicate users and bricks every request
**Problem:** `users.email` is UNIQUE but case-sensitive and signup stores it as typed (app/api/auth/signup/route.ts:112-116), so `Alice@example.test` and `alice@example.test` can coexist today. On such a DB the design's `CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email_lower ON users(lower(email))` throws `UNIQUE constraint failed: index 'idx_users_email_lower'` (verified with bun:sqlite 3.53.4). It runs inside `initMasterSchema`, which `getDb()` calls before setting `masterInitialized = true` (lib/db/connection.ts:192-195), so every subsequent `getDb()` re-runs the migration and re-throws: all API routes including /api/auth/login return 500 until someone fixes the rows by hand. The same collision also prevents the implied `UPDATE users SET email = lower(trim(email))` backfill from running against the existing case-sensitive UNIQUE column.

**Fix:** Before creating the index, run `SELECT lower(trim(email)) AS k, COUNT(*) AS n FROM users GROUP BY k HAVING n > 1`. If it returns rows, log them, create only a non-unique `idx_users_email_lower` and enforce uniqueness in `insertUser`/admin create via `getUserAuthByEmail`; otherwise `UPDATE users SET email = lower(trim(email))` and then create the unique index. Wrap the whole master migration block in one `db.transaction(...).immediate()` so a partial failure cannot leave the DB half-migrated, and make `getDb()` tolerate a failed optional index (never block the login route on it).

### [MAJOR] §3.1 rules / §5.1 / §5.3 — INSERT OR REPLACE on user_accounts resets role to manager; POST /api/accounts persists the raw client body for existing accounts
**Problem:** `addUserAccountLink` is `INSERT OR REPLACE INTO user_accounts (userId, accountId)` (lib/db/users.ts:67-75). Once `role TEXT NOT NULL DEFAULT 'manager'` exists, REPLACE deletes the row and reinserts it with the default: a stored `viewer` becomes `manager` and `grantedByUserId/grantedAt` become NULL (verified with bun:sqlite). The only production caller is `POST /api/accounts` (app/api/accounts/route.ts:27-39), which for an existing id passes the current session-account guard and then calls `upsertAccount({ ...payload, id, ownerUserId })` with the untrusted body (including `dbPath`, which `persistAccountRow` writes, lib/db/rowParsers.ts:166-186) followed by `addUserAccountLink`. Scenario after this design: viewer V of shared mailbox A re-POSTs A's email from the UI's 'add mailbox' form; V's membership is upgraded to manager, and because §5.3 blanks `imap.host/user` for viewers, V's copy overwrites the real IMAP host/user with '' so background sync (which reads only the DB, lib/syncOperation.ts:254-255) fails for every member. `saveUserAccounts` (users.ts:54-65) has the same role-dropping problem and `saveUsers` (19-30) cannot carry `passwordHash` because §3.1 forbids it on the `User` type it accepts.

**Fix:** Change `addUserAccountLink` to `INSERT INTO user_accounts (userId, accountId, role, grantedByUserId, grantedAt) VALUES (?, ?, ?, ?, ?) ON CONFLICT(userId, accountId) DO NOTHING` and add an explicit `upsertUserAccountLink(..., { role, grantedByUserId })` with `DO UPDATE SET role = excluded.role, ...` for admin grants only. In `POST /api/accounts`, when the id already exists require `manager` on that account and go through `patchAccount`/`mergeAccount` with the §5.3 whitelist (strip `id`, `ownerUserId`, `dbPath`, and treat blank `imap.host/user/password` and `smtp.*` as 'unchanged', mirroring `mergeDeeplForPatch`); never call `upsertAccount` with a request body. Delete `saveUsers`/`saveUserAccounts` (or make them throw) instead of 'extending' them, since the `User` type cannot carry the hash and no production caller remains after signup is rewritten.

### [MAJOR] §6.1 / §3.2 rules (commentCount, lazy row creation) — No atomicity rule for collab mutations: lazy-create races, lost commentCount increments, and deferred-transaction BUSY under a running sync worker
**Problem:** The design says rows are created lazily and `commentCount` is 'maintained on insert/soft-delete' but does not say how. PATCH `.../collab` must validate the assignee against master `user_accounts` (async, different DB); if that await sits between the shard `SELECT` that decides 'row absent' and the `INSERT`, two concurrent first mutations on the same thread (two agents, or UI + MCP) hit the `threadId` PRIMARY KEY and the second request 500s. A JS read-modify-write (`state.commentCount + 1`) across any await loses increments the same way. bun:sqlite `db.transaction()` is DEFERRED; when the recompute/sync worker holds the shard write lock, a deferred read→write upgrade in WAL mode fails immediately with SQLITE_BUSY (busy_timeout does not apply to that upgrade), and `withDbWriteRetry` (lib/dbWriteRetry.ts:30-37) only retries on BUSY/LOCKED, so the whole read+write must be inside one immediate transaction for the retry to be correct. Finally, a Next-process write that raced the worker's remap re-creates a row under the dead old threadId (orphan) and the user's change is invisible.

**Fix:** State in §6.1: all master-DB validation (membership, role) happens before touching the shard; each mutation is one synchronous `db.transaction(fn).immediate()` wrapped in `withDbWriteRetry`, containing `INSERT INTO thread_collab_state (...) VALUES (...) ON CONFLICT(threadId) DO UPDATE SET ...` (no SELECT-then-INSERT), the comment INSERT/soft-delete, `UPDATE thread_collab_state SET commentCount = (SELECT COUNT(*) FROM thread_comments WHERE threadId = ? AND deletedAt IS NULL)` and the activity INSERT; inside the same transaction verify `EXISTS (SELECT 1 FROM messages WHERE threadId = ? AND COALESCE(deleted,0)=0)` and return 404/409 otherwise so a write can never land on a threadId that a concurrent remap just retired. Also specify that `applyBadgeFilters` emits `0 = 1` for `assigned-to-me` when `viewerUserId` is absent (legacy sessions can carry `userId = account.id`).

### [MAJOR] §3.2 rules (remap only in recomputeThreadIdsForAccount) — threadIds are rewritten outside the recompute path (resync, INSERT OR REPLACE upserts), orphaning collab rows with no re-attach rule
**Problem:** The design assumes threadIds only change in `recomputeThreadIdsForAccount`. But `resyncMessage` re-resolves threading for the single message (lib/mail/resyncMessage.ts:51-56) and `upsertMessages` writes rows with `INSERT OR REPLACE INTO messages (... threadId ...)` using the incoming `message.threadId` (lib/db/messages/upsert.ts:184-187, 496-500); `findMessageById` does not even read the existing threadId (144-148). Scenario: C arrived before its parent B and got threadId <B>; B later arrived under <A>; a user assigns and comments on the thread shown for C (state row keyed <B>). The user hits 'Re-sync message' on C: threading now resolves C to <A>, the row is replaced, and the assignee/status/comments keyed <B> disappear from every list and the thread view; 'never pruned' only keeps the row in the table. `anchorMessageId` is declared 're-attach aid' but no code path reads it.

**Fix:** Extend `findMessageById` in upsert.ts to select `threadId`; when an existing row's threadId differs from the incoming one, collect `(old -> new)` and call the same `remapThreadCollab`/thread_topics remap inside the upsert transaction (reuse the §3.2 policy, including the 'old id still has messages' rule). Independently define the `anchorMessageId` fallback: `getThreadCollabState(s)` looks up by threadId first, then by `anchorMessageId IN (thread root Message-IDs)` and lazily re-keys the row. Add a test that re-syncs a message whose threadId changes and asserts the state follows it.

### [MAJOR] §4.2 step 4 / §8 compatibility — Legacy IMAP fallback assigns the mailbox owner's userId to any member, corrupting actor/assignee data and granting owner rights
**Problem:** The legacy branch is kept 'unchanged', and today it resolves the session user as `ownerUserId ?? linked user ?? emailUser ?? account.id` (app/api/auth/login/route.ts:60-69) after locating the account by email, imap.user or user_accounts link (29-37). Migration scenario the design itself targets (§8: 'users keep logging in with IMAP credentials until they set a password'): member B (viewer, no hash) enters b@example.test plus the shared mailbox's IMAP password. B gets `session.userId = A` (the owner), i.e. `manager`, and every `thread_activity.actorUserId`, `assigneeUserId` and comment author written by B is A; `assigned-to-me` for B shows A's queue. The activity log the design calls 'honest' (D5) is wrong for every not-yet-migrated user on a shared mailbox.

**Fix:** In the legacy branch resolve `emailUser.id` first when the typed (lowercased) email matches a `users` row that has access to the account; fall back to `ownerUserId` only when no such user exists. Better: if the matched user has a membership on an account with more than one member, refuse the legacy path with the generic 401 and surface 'Set an app password' through the admin reset flow, so shared-mailbox identities are never derived from IMAP credentials.

### [MINOR] §3.1 idioms (initMasterSchema) — Migration block is non-transactional and not tolerant of a concurrent ALTER from CLI scripts
**Problem:** `initMasterSchema` does `PRAGMA table_info` then `ALTER TABLE ... ADD COLUMN` with no transaction or try/catch (lib/db/schema.ts:647-688). Next runs it at startup (instrumentation.ts:11-12) before any worker child exists, so Next vs. sync/recompute workers do not race in practice. But `scripts/recomputeThreads.ts`, `scripts/diagnoseSyncState.ts` and the backfill scripts each call `getDb()` in their own process; an operator running one during a server restart after upgrade makes the loser throw `SQLITE_ERROR: duplicate column name` (verified), which `withDbWriteRetry` does not retry and which aborts `getDb()` (and with the users-index issue above, keeps aborting).

**Fix:** Run the check+ALTER block inside `db.transaction(() => { /* re-read PRAGMA table_info here */ ... }).immediate()`, or catch errors matching `/duplicate column name/` per ALTER and continue. Keep `CREATE TABLE/INDEX IF NOT EXISTS` outside, as today.

### [MINOR] §6.4 / §5.3 mergeAccount — user_account_prefs PUT semantics undefined; clients write full objects, so team defaults get frozen per user or personal prefs leak into account.settings
**Problem:** The client PUTs the whole settings object (useAccountController.ts:331-344; `getTabSaveSnapshot('preferences')` in lib/accountSettings.ts:84-95 sends full `threading/layout/appearance`), and `normalizeAccountSettings` (accountSettings.ts:4-27) fills every UI key with a default on every persist, so `account.settings` is always 'complete'. With the resolution 'defaults < account.settings < user prefs' and an unspecified PUT, the natural port stores the resolved effective object as the user's prefs: each user who opens Preferences freezes a copy of all team defaults and a manager changing `layout.defaultView` for the team never reaches them. Conversely, a manager whose tab still PUTs the merged object to `/settings` (shallow top-level merge in rowParsers.ts:153) turns their personal prefs into team defaults.

**Fix:** Define `PUT /prefs` as a sparse deep-merge (PATCH semantics): only keys present are written, `null` deletes a key, and the client sends only keys the user explicitly changed (diff against `account.settings`). Keep `effectiveSettings` separate from `account.settings` on the client. Have `/settings` and `PUT /api/accounts/[id]` strip the per-user keys (`layout`, `appearance`, `calendar.weekStartsOn`, `threading`, `defaultSignatureId`) unless the request is explicitly the team-defaults form.

### [MINOR] §4.5 / §5.4 / §6.2 (cross-DB references) — assigneeUserId dangles across the master/shard split after user delete or membership revoke; 'unassigned' filter misses those threads
**Problem:** `assigneeUserId` lives in every shard with no FK (§3.2) and neither `DELETE /api/admin/users/[userId]` (§4.5) nor `DELETE .../members/[userId]` (§5.4) touches shards. After a revoke or delete, threads remain assigned to a non-member: the `unassigned` badge (`assigneeUserId IS NULL`) excludes them, `assigned-to-me` never shows them to anyone, and the assignee picker renders an unknown id. The PATCH-time 'non-member assignee → 400' check does not cover this.

**Fix:** On revoke, run in that account's shard `UPDATE thread_collab_state SET assigneeUserId = NULL, assignedAt = NULL, updatedAt = ?, lastActivityAt = ? WHERE assigneeUserId = ?` and write one `unassigned` activity row per thread with `actorClientId = 'system'`; on user delete iterate `getAccounts()` and do the same (skip shards that fail to open, log them). Document this in §5.4/§4.5.

### [MINOR] §6.2 enrichment call sites — Single-message sites do not use the batched topic helper; collab enrichment list is inaccurate
**Problem:** `messages/[messageId]/route.ts:33-41` calls `getTopicsForThread`, not `enrichMessagesWithThreadTopics`, and the MCP server has four batched sites (`listMessagesForFolder` lib/mcpServer.ts:626 and three branches of `searchMessages` at 687/721/751) plus the single-message output of the topic-update tool (518). Following the design literally ('same sites as enrichMessagesWithThreadTopics') leaves the single-message REST route and MCP single-message outputs without `collab`, so a thread opened by direct link shows default state while the list shows the real one.

**Fix:** List explicitly: batched helper at listMessagesHandler.ts:68, threads/route.ts:49, related/route.ts:40, thread/related/route.ts:45, mcpServer.ts:626/687/721/751; single `getThreadCollabState(accountId, message.threadId)` at messages/[messageId]/route.ts:33 and in every MCP tool that returns one message. Order relative to topics is irrelevant (independent fields) but both must run before the response is serialised.

# LENS: frontend-mobile

## Verdict
The theming core of §7.1 is sound: the `@layer theme, base, radix, legacy, components, utilities` statement before `@import "tailwindcss"` fixes layer order (Tailwind's own `@layer` statement cannot reorder it), `@radix-ui/themes/styles.css` (3.3.0) contains no `@import`/`@layer` and is exported via `"./*"`, so `layer(radix)` is inlined by Tailwind's resolver before Next/Turbopack sees it; next-themes with `storageKey="noctua:theme"` is value-compatible with the existing 'dark'/'light' key and Radix `appearance="inherit"` (ThemeRoot never touches documentElement, dark tokens key off `:is(.dark,.dark-theme)`); MailClient only uses `replaceState` and Next's patched `pushState` makes the mobile history entry safe. What is not implementable as written is §7.2 mobile and §9 ownership: compose always goes to the inline slot inside the reading pane (which the mobile `list` view hides), deep links/notifications bypass the tap that sets `thread`, unmounting panes kills the scroll/virtualization refs, the z-index plan (shadcn at 9996 above Radix 9995) freezes Radix confirm dialogs opened from the settings frame, Tailwind preflight (not mentioned) strips list bullets and heading sizes from the editor/markdown surfaces, `next/font/google` breaks hermetic Docker/Tauri builds and cannot reach the HtmlMessage srcdoc, and the pixel-width plumbing (`MessageListPane` inline width, `listWidth` prop) collides with `ResizablePanelGroup`. Several files that must change (`composition/**`, `messagelist/MessageListPane.tsx`, `MessageListOrchestrator.tsx`, `MessageViewPane.tsx`, `BottomStatusBar`, `HtmlMessage.tsx`) are assigned to nobody, and "MailClient render tree only" is not a real boundary. Fix the mobile compose/nav model, the z-index direction, preflight, fonts, and the ownership table before implementation starts.

The mobile sidebar sheet (FolderTree, Radix-styled), the settings sheet (Radix tab contents, Select, DropdownMenu) and the compose sheet (ComposeModal uses `--space-6`, `--radius-5`, `--color-panel-solid`) therefore render unstyled unless each generated wrapper is modified to forward `container`, which the `shadcn add` diff workflow will keep overwriting.

**Fix:** Instead of patching portals, wrap the content of the three hosting shells with Radix `<Theme asChild>` (the pattern Radix Themes uses for its own portals, re-establishing tokens and data-attributes) and keep `container={document.querySelector('.radix-themes')}` only for custom `createPortal` calls like CalendarPopover.tsx:365. State this in §7.1 and add a DOM test that mounts a kept component inside the settings Sheet and asserts `getComputedStyle(...).getPropertyValue('--space-2')` is non-empty.

### [MAJOR] §7.1 / §6.4 — Two sources of truth for theme: next-themes localStorage vs `user_account_prefs.theme`
**Problem:** §7.1 makes next-themes (localStorage `noctua:theme`, pre-hydration script) the theme authority; §6.4 stores `theme: "light"|"dark"|"system"` per user per mailbox on the server. Nothing says which wins or when: switching mailbox could flip the theme, a new device would paint the localStorage/system theme first and then flip after prefs load, and the Preferences tab writing prefs would not update next-themes (or vice versa).

**Fix:** Remove `theme` from `user_account_prefs` and keep it a device preference (today's behaviour), or define it as 'seed only when localStorage has no value' and have the Preferences tab call `setTheme` as well. Pick one and write it in both sections.

### [MINOR] §7.1 Stack — shadcn CLI defaults do not match the design (Tailwind must pre-exist, components land in root `components/`, globals.css gets rewritten)

### [MINOR] §7.1 next-themes — `resolvedTheme` is undefined on first render: every HtmlMessage iframe is rebuilt once after mount for dark users, and `suppressHydrationWarning` must move to `<html>`

**Fix:** Put `suppressHydrationWarning` on `<html>` (keep it on `<body>` only if still needed for the runtime-config script).
