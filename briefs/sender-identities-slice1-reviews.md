### Findings (most severe first)

1. **P2 — Already migrated shards acquire an unnecessary writer lock, breaking collaboration's cold-reader contract.** `lib/db/schema.ts:1408–1412`, called by `lib/db/connection.ts:261` and `initAccountSchema` at `schema.ts:1277`. The WeakSet only helps a previously seen handle: a new handle always executes `BEGIN IMMEDIATE` before checking whether the three columns already exist. A scratch two-connection WAL probe on a completely migrated table demonstrated that plain SELECT succeeds under another connection's writer lock, while `ensureSenderIdentityMessageRuntimeSchema(reader)` throws `database is locked` with busy_timeout=0. With the usual timeout it blocks instead. This directly conflicts with `133bddc:lib/db/connection.collab.test.ts:67`, **“cold shard reader succeeds under a held writer lock without schema writes”**; its companion test requires real schema creation to retry at the async connection boundary. **Fix:** inspect PRAGMA without a write transaction first and mark a complete schema as initialized. Only when columns are missing, enter the immediate transaction and re-inspect using `ensureTableColumns`; retain collaboration's async `withDbWriteRetry("initAccountSchema", ...)` boundary. Re-run both collaboration connection tests on the merged result. Existing migration tests only open an uncontended DB and miss this integration regression.

2. **P2 — `from:me` / `with:me` become intersections of all identities.** `lib/db/messages/query.ts:599,621` expand one `me` token into several terms, but `applyAddressSearchFilters` at `:544–547,561–571` ANDs those terms. A mailbox with primary+alias and one ordinary alias→customer message returns one unfiltered result, **zero for `from:me`, zero for `with:me`** (isolated scratch regression). Adding even a disabled historical identity can break these searches, since the own-address set intentionally retains it. **Fix:** represent one `me` term as an OR group of canonical own addresses; preserve AND semantics between independently entered search terms. Add message/thread/count regressions for primary, enabled alias, disabled alias and unrelated sender. Avoid introducing another substring-based identity test in the fix.

3. **P2 — Consumer migration still bases decisions on addresses in display text.** `app/components/mailclient/composition/composeInitState.ts:291–298` obtains comparison addresses through `getPrimaryEmail` (`:26–27` → `clientHelpers.extractEmails`, a whole-string regex); `lib/topicSignals.ts:95–99` still calls its regex-based `extractEmailAddresses` (`:24–32`); `lib/mail/categorization/classifier.ts:179` still pre-extracts using `extractEmailAddress` (`:107–111`). The new exact helper is applied only *after* lossy/incorrect extraction. For `"alias@example.test" <customer@example.test>` and own alias `alias@example.test`, scratch probes show: the customer is dropped from reply-all CC, topic signals are `[]` instead of customer, and string-form classifier input returns `skip:sender-is-account` for an external sender. Structured IMAP address input does not exhibit the last case, but string input is an advertised classifier seam. **Fix:** use `parseAddressEmails` on complete recipient/from entries before comparisons and signal extraction; keep display parsing only for presentation. Add the misleading-display-name regression and punctuation/IDN cases to consumer tests. The existing tests use uncomplicated bare addresses and do not prove the no-display-text-logic requirement.

4. **P2 — The two migrated MCP topic consumers still receive only the primary address.** `lib/mcpServer.ts:687,721` now call `getOwnAddresses(context.account)`, but `resolveAccountContext` at `:336–337` replaces its account with `resolveMcpToolContext`'s live account; `lib/mcpAuth.ts:29–30` constructs that account with `mapAccountRow`, which does not load identities/ownAddresses (`lib/db/rowParsers.ts:143–175`). Unlike REST's `getAccountById` path, this loader is not enriched. The optional identities argument is omitted, so alias and disabled identities are absent from these calls. This matters for legacy/stale persisted signals and suggestions; merely changing the call expression did not migrate the effective data flow. **Fix:** load `getAccountOwnAddresses(context.accountId)` once per MCP operation, or enrich the live mailbox context through a shared synchronous loader without weakening token/live-role checks. Add token-bound MCP topic tests for configured/disabled aliases and cross-mailbox exclusion. Identity MCP CRUD/send tools themselves correctly remain Slice 2 work.

5. **P2 — Legacy IDN authors remain “received” in exact SQL, and NULL repairs occur after aggregation.** `lib/db/ownAddressSql.ts:6–9` only applies SQLite `lower(trim(...))`; it does not canonicalize IDNA, while `getOwnAddresses` does. `lib/db/threads.ts:349–361` calculates thread dates at `:351` before repairing NULL `fromEmail` at `:354–359`, and never repairs non-NULL old authors. A scratch real-shard case with external date=1000 and own `alias@bücher.example` date=2000 produced latestReceived=2000 after the first NULL-author recompute, 1000 after the second; with legacy non-NULL `fromEmail='alias@bücher.example'`, recompute still produced 2000. The own set contains `alias@xn--bcher-kva.example`. Old code populated angle-bracket fromEmail without this canonicalization, so populated legacy rows are relevant too. **Fix:** canonicalize affected legacy derived author fields on explicit recompute before deriving thread aggregates, including already populated noncanonical IDN forms, and retain exact bound comparisons plus all-outgoing MAX fallback. Test legacy bare/angle, NULL/populated fromEmail, Unicode/punycode equivalence and an external substring lookalike. This is separate from the new identity uniqueness index, whose normal API write path stores ASCII canonical addresses correctly.

6. **P3 — The published handoff is useful but incomplete as a client contract.** `doc/SENDER-IDENTITIES.md:10–19,39–47,65–69` names envelopes but omits the full SenderIdentity field/type/nullability contract; POST defaults; address/display/ID bounds; existing `defaultSignatureId` and its `""`/null semantics; the exact `{ok:true,job}` polling envelope; nullable/ephemeral recomputeJob and its complete fields; and explicit settings-save/refresh guidance. `lib/data.ts:94–106`, `lib/senderIdentities.ts:11–22`, `lib/accountPrefs.ts:4–13`, and `app/api/_helpers/recomputeJobs.ts:76` are needed to reconstruct these. GET prefs returns a sparse object without null deletion markers; the text currently combines GET and PUT key types. **Fix:** publish these shapes and distinctions, the authorization error-shape exception, and a clear planned Slice 2 send/draft/calendar/MCP contract (or an exact stable design reference). ### Contract/reuse/schema assessment

REST roles conform to the design/team matrix: viewer reads identities and owns prefs; only manager writes identities; editor remains insufficient; admin without membership gets no mailbox access. Existing auth/MFA/origin helpers are reused, including their pre-existing denial envelopes (not all auth/role failures carry a domain `code`). Validated prefs run inside the existing synchronous sparse-merge transaction; no duplicated merge implementation or async nested transaction was introduced. Audit uses the existing redacting writer; account patching retains `mergeAccount`'s field whitelist. New Account.ownAddresses is not accepted from a request patch or stored in accounts. Personal fields are stripped even with teamDefaults=true, as required for identity/signatureOverride privacy.

The identity normalization/parser is intentionally stricter than the existing presentation helper in `lib/senderIdentity.ts`; adding it is reasonable. Keeping old extraction helpers *before* the new helper, however, creates divergent address semantics (finding 3). `lib/db/messages/identityMetadata.ts` centralizes hydration rather than copying it into each mapper; `ownAddressSql.ts` likewise shares SQL construction. `getIdentitySignatureIds` reads account signature IDs in the SQL layer. Exported setDefault/disable functions and the pure resolver are used by tests or future slices; absence of UI callers is intentional slice staging, not dead code. No new TODO/FIXME/temporary marker was found in the feature modules; the `End replacement metadata preservation`/`End sender identity metadata` comments in upsert are unnecessary boundary comments, not unfinished functionality. `ownAddressList`'s compatibility comment describes a purposeful string-or-array seam. `nice` in threadRecomputeJobs is an unrelated platform dependency worth avoiding/justifying separately, but it did not fail in this Linux review.

Schema is additive/idempotent and uses existing `ensureTableColumns`/PRAGMA inside immediate transactions, with no table rebuild or startup message refetch/rewrite. No delivery-column indexes are needed; `(accountId,email)` serves scoped listing/uniqueness, and the partial default index enforces at most one. Service logic supplies at least one. `NOCASE` itself handles ASCII only; correctness for supported API addresses comes from lowercased ASCII local parts + URL/IDNA domain conversion **before storage** (`ownAddresses.ts:11–18`). Unicode local parts/SMTPUTF8 are rejected; SQL alone does not prevent raw noncanonical Unicode/punycode duplicates. Add a service duplicate-equivalence test for Unicode and punycode, rather than claiming the uppercase ASCII migration test proves Unicode collation. Legacy seed has a permissive fallback when an old account.email is outside the validator; document that compatibility limit. Finding 5 concerns legacy message SQL, not a failure of normalized API uniqueness. Finding 1 is the important PRAGMA/readiness issue: correct DDL idempotency is insufficient if every cold read takes a writer lock.

### R2 — Medium: recompute retries can enqueue unlimited simultaneous mailbox rebuilds

- **Location:** `lib/threadRecomputeJobs.ts:21`; reachable from `app/api/accounts/[accountId]/identities/route.ts:48`, and identity creation at `lib/senderIdentities.ts:77`.
- **Scenario:** An authenticated mailbox manager repeatedly submits same-origin `PUT {recompute:true}` while a previous job is running. Every request starts a new account-wide worker. `identityRecomputeJobs` records only the latest ID; it does not deduplicate, bound concurrency, or rate-limit requests. Separate identity creates also start separate workers. These jobs read/rebuild the same shard and use the shared master DB; `nice` lowers CPU priority but does not bound work or contention.
- **Repro:** `regressions.test.ts`, test **R2 repeated manager recompute retries coalesce while a job is running**. Three real authenticated route calls return 202 and three distinct running job IDs. The narrow `Bun.spawn` spy records spawn requests and supplies unresolved child promises, avoiding actual load. Expected one active job; observed three. This establishes unbounded enqueue behavior, not a measured outage.
- **Fix:** Make create/retry share a mailbox-scoped job slot, coalesce running work, and enforce bounded scheduler concurrency plus a retry cooldown/rate limit. Preserve the public job/status contract and serialize the slot across server processes where applicable. Keep viewer/editor denial checks.

### R1 — Medium: adding any alias breaks `from:me` and `with:me` search

- **Location:** `lib/db/messages/query.ts:599` and `:621`; expansion is consumed by `applyAddressSearchFilters` at `:544` and `:560`.
- **Scenario:** A mailbox has primary and alias identities. Search expands `me` into separate ordinary address terms, but the SQL builder combines each term with `AND`. A message sent by only the primary or only the alias cannot satisfy both author predicates. The same intersection bug affects participant searches. Disabled identities further increase the required conjunction.
- **Repro:** `regressions.test.ts`, test **R1 from:me and with:me match any historical own address rather than requiring all**. Store two messages, one from each own address to an external customer. Both searches return total **0**, expected **2**. These query helpers also back thread/count/group projections and MCP standard search.
- **Fix:** Represent one `me` token as a grouped OR over historical own addresses, keeping separate user-entered search terms conjunctive. For authors use the exact normalized author comparison rather than introducing substring ownership matching. Keep list/count/group/thread semantics aligned.

### R3 — Medium: a shared-shard row-ID change discards preserved delivery metadata

- **Location:** `lib/db/messages/upsert.ts:295`–`:297`; replacement snapshot keyed only by row ID at `:282`–`:286`; persistence at `:553`–`:555`.
- **Scenario:** A and B share a shard and receive the same Message-ID. A occupies the base row ID; B receives the account-suffixed ID. A's copy later disappears. B's next envelope-only replacement selects the now-free base ID. Its old snapshot is stored under the suffixed ID, so the lookup misses it and writes NULL for B's previously captured delivery arrays and draft identity marker. Ordinary non-replacement deduplication can likewise discard the prior same-copy row before transferring its metadata.
- **Repro:** `regressions.test.ts`, test **R3 shared-shard envelope replacement preserves B metadata after A's base copy disappears**. Store distinct A/B observations, remove A's base copy, then replace B's folder using envelope-only input. B loses `deliveredTo`, `originalTo`, and `senderIdentityId`, all observed undefined instead of its stored values. No cross-account disclosure was observed; the defect is same-copy metadata loss.
- **Fix:** Resolve the prior account/folder/UID/message copy before choosing/reusing a row ID, including replacement snapshots and same-copy deduplication rows. Reuse its stable row ID or transfer only that exact copy's metadata before deletion. Include the header Message-ID in a scoped snapshot index where needed; never merge distinct UID/folder copies. After thread-collaboration, capture this snapshot under the existing immediate writer lock.

### R4 — Low: valid commented delivery addresses are discarded

- **Location:** `lib/ownAddresses.ts:25`–`:26`, used by `lib/mail/imap/parser.ts:229`.
- **Scenario:** A Bcc-only message records `X-Original-To: alias@example.test (original recipient)` and `Delivered-To: primary@example.test`. The valid address comment causes the strict configuration-address normalizer to reject the entire observed recipient. The original-recipient array becomes empty, and reply identity resolution selects the primary instead of the alias. This changes the contract's recipient-evidence priority; sending as aliases remains a later slice.
- **Repro:** `regressions.test.ts`, test **R4 valid recipient comments retain Bcc-only alias evidence and select that alias**. Expected `{originalTo:["alias@example.test"],selection:"alias"}`; observed `{originalTo:[],selection:"primary"}`.
- **Fix:** Parse observed RFC mailbox syntax, including comments, before canonical addr-spec validation. Keep the configuration validator strict and the shared client helper browser-safe. Preserve exact mailbox matching, order, deduplication, the 32-address cap, and rejection of actual control/header injection.

### R5 — Low: MCP own-address topic filtering omits aliases

- **Location:** `lib/mcpServer.ts:687` and `:721`; its account originates from the unhydrated `mapAccountRow` in `lib/mcpAuth.ts:28`.
- **Scenario:** Identity configuration has committed, but its documented asynchronous rebuild is pending or has failed. HTTP handlers load an account with `ownAddresses`; the live MCP token context does not. `getOwnAddresses(context.account)` therefore returns only the primary address. Stale historical alias recipient signals can still create unrelated topic suggestions through MCP, while the HTTP-equivalent helper excludes them. A successful rebuild removes this particular stale signal, but a failed rebuild is an explicitly supported state.
- **Repro:** `regressions.test.ts`, test **R5 MCP ignores historical alias exclusion while a configured rebuild is pending or failed**. Learn a topic from an alias-recipient thread before configuring the identity; retain those signals to model a failed worker. The helper with the full live own-address set returns no suggestions; a real authenticated `search_messages` MCP thread request returns the learned topic with suggestion score **2**.
- **Fix:** Hydrate the live token context with scoped sender identities or load `getAccountOwnAddresses(context.accountId)` once per tool/request and pass it to both enrichment branches. Preserve live membership rechecks and mailbox binding. This is a consistency defect, not a token authorization bypass.

### R6 — Low: first legacy IDN recompute derives received dates before repairing authors

- **Location:** `lib/db/threads.ts:351` precedes the author repair at `:354`–`:360`; legacy fallback at `lib/db/ownAddressSql.ts:6` does not canonicalize IDN domains.
- **Scenario:** A legacy message has NULL `fromEmail` and Unicode-domain `fromAddr`, and the corresponding identity normalizes to punycode. The first rebuild compares raw Unicode against the canonical own-address set, counting an outgoing alias message as received. It subsequently repairs `fromEmail`, but never recalculates the stored date in that invocation. Topic signals and thread received-date ordering consequently disagree until another rebuild.
- **Repro:** `regressions.test.ts`, test **R6 first recompute repairs IDN legacy authors before deriving latest-received dates**. Inbound at 1000 and outgoing `alias@bücher.example` at 2000 share a thread. After one rebuild the author is correctly repaired to `alias@xn--bcher-kva.example`, yet `latestReceivedDateValue` remains **2000**, expected **1000**.
- **Fix:** Complete the account-scoped NULL-author repair before computing thread summaries and signals, or recompute summaries after repair. Preserve the all-outgoing MAX fallback and collaboration thread IDs.
