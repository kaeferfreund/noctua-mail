### Findings, most severe first

1. **HIGH — Invitations retain admin-creation authority after their issuer is demoted or banned.** `lib/db/userProvisioning.ts:24`, `lib/userLifecycle.ts:30`; final consumption at `lib/db/userProvisioning.ts:59`.

   **Scenario:** admin A issues an email-bound invitation with role `admin`; admin B then demotes or permanently bans A. The invitee can still redeem A's invitation with a chosen password and create a new admin identity. This defeats the explicitly requested issuer-revocation boundary. The missing authority check also permits the optional mailbox verification calls on what should be a rejected request.

   **Reproduction:** retained `security-controls.test.ts`, tests `F1 observation: demoted issuer invite still provisions another admin` and `F1 observation: banned issuer invite still provisions another admin`. Each uses real library users, enrolled admin sessions and `issueOnboardingInvite`; B performs the actual lifecycle update before `provisionUser` runs. Both observe successful provisioning, `auth_user.role='admin'`, and **two** injected IMAP/SMTP calls. These are observational tests: a passing test demonstrates the defect, not acceptance of the control. No mailbox network connection occurs.

   **Cause:** the invite insert records no issuer identity. Preflight/reservation validate email, expiry, capacity, role and bootstrap state, but never the issuer's current authority; final consumption cannot check it either.

   **Specific fix:** persist the issuing admin ID for admin-issued invitations, with an explicit separate provenance for operator/bootstrap invitations. Reject a missing, disabled or demoted issuer in the initial preflight **before** credential verification, recheck inside reservation, and condition final consumption on current issuer authority so revocation during library/network awaits cannot complete provisioning. Alternatively revoke all outstanding invitations atomically with issuer demotion/ban, while retaining a final transactional authority check for races. Preserve intentional operator/bootstrap invites. Change these two probes to assert 403, no new identity, no reservation and zero verification calls; add the during-await revocation case.

2. **MEDIUM — Operator recovery runs against a live app and cancels its active security operation.** `scripts/recoverTeamAuth.ts:9`, `scripts/recoverTeamAuth.ts:14`–18.

   **Scenario:** an operator invokes the documented command with `--application-stopped` while the app is still running. That argument is only an assertion; no lock or liveness check enforces it. The script initializes auth, reconciles journals and issues recovery against the live datastore. Reconciliation is allowed to cancel active user slots that a live request still owns, violating the serialization prerequisite.

   **Reproduction:** retained test `F2 observation: operator script issues recovery while app and its security intent are live`. Inside an isolated network namespace it creates a synthetic datastore, attaches a real Noctua/Better Auth handler to that same database, serves it on **127.0.0.1:3786**, and holds a `security.synthetic-live` operation. It spawns the actual `scripts/recoverTeamAuth.ts --application-stopped --confirm-personal-handover --user-id <synthetic-id>` with an explicit synthetic environment. Observed: the app answers `/api/ba/ok` before and after; child exit is **0**; a reset link is emitted once; an `actorUserId='operator'` recovery audit is written; the previously active operation becomes `{slot:null,state:'cancelled'}`. The captured reset URL is not retained in this report or printed by the probe.

   **Specific fix:** acquire and retain an OS-enforced, datastore-scoped application lifetime lock before auth initialization. Require the operator command to acquire that same lock exclusively, nonblocking, **before `getAuth()`**, and refuse without touching journals if the app holds it. Keep the confirmation flags for operator intent. A process/port check alone cannot safely protect another app instance using the same data directory. Add regression assertions for nonzero exit, no link/audit and unchanged live intent while the app holds the lock, plus successful recovery after lock release.
