## Findings

### P2-A A From change can be undone by switching editor formats

- `app/components/mailclient/composition/useComposeController.ts:64` (also :65–70); `app/components/mailclient/composition/ComposeMessageField.tsx:292`.
- Scenario: open a new HTML composer with the shared signature; switch to Text without typing; choose another From; switch back to HTML. The selector retains the new identity but the signature reverts to the old identity's text. The same occurs through Markdown. Programmatic signature changes update only the active representation and never mark that representation as the last edited one; conversion then reuses stale HTML.
- Probes in `sender-identities-slice3-regressions/sender-compose-review.dom.test.tsx`: `P2-A From change after HTML to Text must survive switching back to HTML` and `P2-A From change after HTML to Markdown must survive switching back to HTML`. Both fail against the pinned checkout. Also reproduced in the production browser: From changed to `demo@monkeydent.test` in Text, then HTML restored the signature containing `alias@example.test`.
- Markdown has an additional tracking problem in this path: HTML conversion turns the address into an autolink, which no longer matches the initializer's escaped Markdown block, so an unchanged signature is treated as edited and confirmation appends a second block.
- Required: make the programmatic edit authoritative for later conversions, flush/cancel pending body updates consistently, and retain safe signature boundaries across each conversion. Preserve authored text and quotes. Add both format-roundtrip regressions; do not satisfy them by dropping the signature or user edits.

### P2-B A transient sender-settings error permanently deduplicates the same reply attempt

- `app/components/mailclient/composition/ComposeOrchestrator.tsx:1182`, :1192–1201, :1281.
- Scenario: the identities/prefs/me snapshot fails once while opening a reply. Clicking Reply again for that same message does nothing, even after the API recovers. The in-flight key is installed before the snapshot request, but its cleanup finally starts below that request; rejection bypasses cleanup.
- Probe: `P2-B a failed sender snapshot must allow retrying the same reply` in `sender-compose-review.dom.test.tsx`. After two attempts the loader was called once, expected twice. The retry never opens the composer. This common message-based initialization path also governs draft and forward opens.
- Required: include the snapshot acquisition in the outer token-aware try/finally that clears the deduplication key. Preserve repeat-click deduplication while a request is actually pending and retain account/user/session staleness checks.

### P2-C Shared signature saves accept templates that prevent compose from opening

- `lib/signatureTemplates.ts:15`; `app/components/account-settings/tabs/SignaturesTabContent.tsx:29`; ingress at `app/api/accounts/[accountId]/settings/route.ts:13` and `lib/mailboxCredentials.ts:87`.
- Scenario: an authenticated manager saves a shared default template containing `{{user.title}}`, or a body of 4,097 `é` characters (8,194 UTF-8 bytes). The service persists it and the actual settings route returns 200. This slice's strict renderer then throws during compose initialization. A persisted default of this shape prevents new compose from opening; it is not presented as an actionable template warning. Existing legacy templates can reach the same new consumption failure.
- Probes in `shared-signature-save.test.ts`: `P2-C shared settings save rejects unsupported placeholder`, `P2-C shared settings save rejects more than 8 KiB`, and `P2-C authenticated shared signature route rejects unsupported placeholders` all fail. The route result is 200, expected 400. `P2-C a persisted invalid shared template must not prevent opening the composer` in `sender-compose-review.dom.test.tsx` also fails with `Failed to open composer: Use only the supported signature placeholders (maximum 8 KiB).` Personal override validation does reject these inputs.
- Required: apply the shared template validator at the authoritative common settings write boundary, including alternate settings mutation entry points, before persistence; reject unsupported placeholders and UTF-8 oversize bodies with a stable error code. Coordinate that server change with its owner. Handle already persisted invalid templates without making compose unusable, with an explicit manager-facing repair warning. The unchanged server ingress is an integration gap exposed by this slice's new renderer, not a claim that identity authorization was weakened.

### P2-D The mobile From control and dropdown overflow the phone viewport

- `app/components/mailclient/composition/ComposeFields.tsx:322`; inherited sizing at `app/components/mailclient/composition/Compose.module.css:134`, :141, :152.
- Scenario: a normal mailbox default label, `QA Shared <demo@monkeydent.test> (mailbox default)`, in a fresh mobile composer. The Select's intrinsic width expands the `1fr` grid tracks; the compose body clips the right side. The dropdown also exceeds the viewport. From details and the dropdown affordance are clipped even though the existing visibility-only browser assertion passes.
- Executed preserved probe: `mobile-from.browser.js`, `P2-D mobile From control and popover fit the viewport`, through the production T3 browser at 360×780 and 390×844. At 360: trigger x=67.5, width=407, right=474.5; popup right=442. At 390: trigger x=108, width=407, right=515; popup right=442. Both control/menu bounds checks fail at both widths. Exact x positions vary with focus-induced scrolling, but the 407 px trigger itself is wider than either viewport.
- Required: allow the From grid cells/trigger to shrink (`minmax(0, 1fr)` and appropriate min-width constraints), wrap or truncate the display presentation accessibly, and constrain/wrap the popup to available viewport width. Verify actual bounds and hit targets at both widths, including mailbox-default and unavailable labels.
