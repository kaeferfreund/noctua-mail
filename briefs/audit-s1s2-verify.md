## Corrections after the deps thread's guard-cost analysis (briefs/perf-writer-guards.md, 2026-10-22 ~23:50 UTC)
- The follow-up note above ("one trigger per table checking the marker once per statement") is WRONG: SQLite only has row-level triggers, so a bulk UPDATE over 5,100 rows evaluates the guard 5,100 times. Measured in real flows: initial sync 5,000 mails +2 % (ranges overlap), incremental sync / recompute / bulk delete / draft autosave / watcher no resolvable overhead; bulk flags 5,100 mails 138 → 184 ms (+33 %), folder move 63 → 70 ms. ~91 % of the overhead is the trigger machinery, not the JS callback; WHEN clauses, deterministic flag or a native function change nothing measurable; compile-only variants would accept a wrongly registered marker. Decision: keep the guards as they are.
- Scope statement: direct writes to message_fts_v2 on an unregistered connection remain possible (SQLite forbids triggers on FTS virtual and shadow tables); the legacy name message_fts is protected by the read-only view, which is what the legacy-binary threat needs. Do not claim "all FTS paths are protected".
