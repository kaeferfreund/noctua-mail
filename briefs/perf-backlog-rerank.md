### Page load and /api/auth/me

There are two separate regressions: more eager UI, and more backend work per newly introduced request.

- `useThreadCollab` requests `/api/auth/me` at **`app/hooks/useThreadCollab.ts:158`**, keyed by apiFetch/accountId/sessionKey (`:173`). It is mounted unconditionally by `MailClient.tsx:2857`, and its identity effect does not guard empty accountId. Bootstrap transitions can therefore trigger more than one invocation; an exact browser request count was not measured. It then fetches `/members` (`:178`) even though a complete collaboration GET also returns members (`collab/route.ts:6`). Pass/reuse current identity and preserve session-scoped membership ordering; do not substitute a persistent authorization cache.
- Auth/me calls `getUserById` again after the session guard already did so (`auth/me/route.ts:11`, `auth.ts:72`). `ensureActiveAccountId` loads account DTOs and updates the session even when the selected account is unchanged (`auth.ts:112`, `:121`); `route.ts:17` then rebuilds the account list via `sanitizeAccountsForClient` instead of consuming that selection. Concurrent duplicate auth/me calls can therefore also cause unnecessary session writes.
- `getAccountsForUser` performs **one account query + N identity queries** (`db/accounts.ts:42`–`:53`). `listAccessibleAccountsForUser` additionally runs role and member readers per account (`accountAccess.ts:30`–`:35`); each member reader loads **every user** via `getUsers()` (`:21`). A successful warm auth/me has **at least 84 direct SQL executions/preparations implied by those application helpers**, including its account selection/update and duplicate user read, **before** Better Auth's own session-query overhead. AND state NOT IN ('complete','cancelled')` has **SCAN user_provisioning**: the existing index is on *active normalizedEmail*, not userId. ### Thread list

The new collaboration list enrichment is **already batched**: `enrichMessagesWithThreadCollab.ts:12` calls `getThreadCollabStates`, whose shard reader chunks by **400** (`db/threadCollab.ts:70`). Normal 300-thread page: one collaboration-state query, not 300. Existing primary key `(accountId,threadId)` supports it.

The dominant old selector remains. Current real-schema plan:

```text
MATERIALIZE flaggedThreads
SEARCH messages USING idx_messages_account_flagged_thread (accountId=? AND flagged=?)
SEARCH threads USING idx_threads_account_latest (accountId=?)
CORRELATED live-message EXISTS
SCAN flaggedThreads LEFT-JOIN
USE TEMP B-TREE FOR ORDER BY
```

On 11k messages / 3,667 threads / 647 flagged messages, the current selector is **149.47 ms**. Replacing only that flagged join/order expression with `EXISTS` uses `(accountId,flagged,threadId)` for each lookup, still sorts, and is **8.83 ms**, same full rows/order in this fixture. This isolates a useful first patch without changing thread membership or storing another derived column. It does not prove tie ordering, all folders, all dates, and pagination; those remain verification work.

Residual costs measured separately: live message count **5.11 ms**, live-thread count **3.65 ms**, page-member projection **10.58 ms**, mailbox-wide date-group count **13.82 ms**. The complete library call was **194.45 ms**. These are different timed series; do not subtract/sum them as an exact end-to-end prediction. Its raw library JSON was **583,492 bytes** for the member page, before route slimming/topic/collab enrichment. This is not an HTTP payload measurement.

### Collaboration events and mailbox summaries

There is **no periodic collaboration-snapshot polling timer** in `useThreadCollab`. Updates come through initial/thread-change fetches, mutation refreshes, and user-wide SSE. The 60-second activity timer only rerenders relative timestamps (`ThreadActivityPanel.tsx:77`), not network calls.

There is nevertheless substantial event amplification:

1. Hook immediately GETs full summaries (`useMailboxSummaries.ts:33`) and GETs again on EventSource open (`:35`).
2. Server debounces events **250 ms per account** then calls `getUserMailboxSummary(user,[accountId])` (`userEvents.ts:67`). Scope is applied **after all accessible-account metadata** is loaded (`mailboxSummary.ts:39`).
3. Client receives the already-computed mailbox counts, applies them locally, then GETs **all summaries again** (`useMailboxSummaries.ts:36`–`:44`). A burst spanning multiple accounts can produce multiple overlapping full GETs; sequence checks suppress stale publication but do not cancel completed/ongoing server work.
4. Each user/tab repeats this work; each thread-collab event refreshes active collaboration/list state, even when another thread changed (`useMailboxSummaries.ts:46`, `MailClient.tsx:2869`). A mutation already GETs its snapshot at `useThreadCollab.ts:296`, then increments collabRevision onCommit, enabling another refresh through `:245` / `MailClient.tsx:2861`.

Actual warmed populated fixture: **12-account summary 17.44 ms, 157 prepare calls + 24 cached-query calls**. A scoped one-account event read still prepares **69 statements**, **10.38 ms**, mostly because access metadata loads all accounts first. Initial mixed fixture (11 empty shards, correctly still probing) was **267 preparations / 21.46 ms**; do not report 267 as a settled nonempty-account steady state. These numbers are library work, not HTTP latency.

Preserve permission rechecks. The final projection at `mailboxSummary.ts:55`, SSE send's transactional authorization at `userEvents.ts:48`, and **5-second liveness** at `authStreams.ts:68` must not be removed or stretched as a performance shortcut. The 15-second SSE heartbeat is also authorized. Drop duplicate snapshots, narrow metadata lookup, and coalesce/invalidate by mailbox/thread instead.

## Studied and not worth doing now

- **Writer-guard tuning:** retain the exact current registration/triggers. This study's remap and write probes retained guards; statement lifetime, scans, and unnecessary work offer much larger grounded wins.
- **PRAGMA optimize / ANALYZE:** never ran either, on master or shard; never propose them. SQLite 3.53.4 planner regression remains explicit in `schema.ts:1143` and the original SQLite brief.
- **Global db.prepare → db.query conversion:** cached query is already used selectively; dynamic IN/filter shapes and statement ownership make a broad change unhelpful. Local stable-loop hoisting is the demonstrated win.
- **Add indexes to every new table:** auth userId/credential/passkey/session indexes, collaboration composite PK and assignee/status indexes, sender account/email index, unread/live summary indexes already exist. Lease/queue tables are capacity-sized; their scans/priority CASE sort are intentional and unmeasured at deployment scale. Sender-identity ORDER BY temp sort has tiny per-account cardinality. The pre-existing from-address expression index also does not justify more recipient expression indexes (`schema.ts:1133`–`:1145`); query semantics/plans need attention instead. Do not index these solely because EQP contains “sort” or “scan.”
- **Remove all collaboration summary scans by adding counters immediately:** new live/unread indexes already narrow them. First prevent repeated all-mailbox recomputation after an already-counted event. Correct denormalized counts across deletes, moves, assignment, migration and shared shards is a larger task.
- **Shrink the thread API to one row per thread, body-table split, or contentless FTS immediately:** still promising architectural options, but high contract/migration cost. Fix the selector and FTS delete identity first. Separate FTS identity, stored-content duplication, and search-driver problems when profiling.
- **Retune busy_timeout/retry settings:** expensive FTS writes and remap preparation lengthen writer hold time. Remove that work before changing lock behavior; master/auth timeout choices are deliberate. Never change withDbWriteRetry in this task series.
- **Move sync into the Next event loop or share bun:sqlite handles across processes:** loses current isolation and does not reduce parse CPU.
- **Redo completed fonts/icons/Markdown converter/draft/probe/typecheck work:** intact. Only the *new collab viewer caller* bypasses the original boundary. The separate settings task must not be duplicated.
- **Radix Themes removal as a quick win:** largest CSS opportunity, but hundreds of component/token/portal interactions and i18n overlap make this a coordinated UI migration. Partial public CSS imports were already measured as no win. No new size claim without a dedicated implementation build.
- **Next config toggles, Lucide deep imports, source maps, image formats:** installed defaults/retained consumers do not establish a new first-load benefit. `compress` already defaults on; optimizePackageImports already covers Lucide; fonts/inline mail images are not next/image startup candidates. Keep worker externalization/tracing.
- **Long-lived caches of user sessions, roles or decoded credentials:** would trade live revocation for small query savings. Batch within a request or avoid duplicate requests, retaining transaction-bound final checks. Crypto itself was already a negligible cost in the old brief.
- **Raising keep-alive or dependency versions:** no measured connection-level bottleneck here; versions are owned by another thread. Tauri cleanup is already done. The remaining workflow guard is useful hygiene, not a performance release blocker.
