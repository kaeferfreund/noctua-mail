## risks
- IMAP password as first factor: the twoFactor plugin enforces TOTP only through an after-hook on /sign-in/email, /sign-in/username and /sign-in/phone-number (better-auth 1.7.12 dist/plugins/two-factor/index.mjs:245-246). A custom IMAP sign-in endpoint skips 2FA unless it re-implements that hook. The only way to stay on /sign-in/email is to override emailAndPassword.password.verify({hash,password}), which has no user context, with an 'imap:<accountId>' marker in the credential row. That is a hack under AGENTS.md. Also, 8 of ~12 mailboxes are shared, and their IMAP passwords cannot identify a person; only personal mailboxes could. A netcup password change would silently change the app login too.
- IMAP_CREDENTIALS_STORAGE=cookie cannot work with Better Auth. Session rows carry no IMAP/SMTP creds, the overlay in lib/credentials.ts is never filled, and IMAP and SMTP fail with 'No password configured'. ## summary
Auth today is a stateless AES-256-GCM cookie, 'noctua_session', sealed with node:crypto and keyed by sha256 of SESSION_SEAL_KEY (fallback 'dev-session-key'). TTL is 24h, and the /me poll extends it on every call. The payload is {userId, accountId, role, exp} plus IMAP/SMTP passwords when IMAP_CREDENTIALS_STORAGE is cookie or both.

**Guards.** requireSessionOr401 is synchronous and copies the cookie creds into a process-global, per-mailbox overlay (lib/credentials.ts). Authorization is the rule 'route mailbox == session.accountId' (requireSessionAccountOr403). The enforcement points are 17 direct call sites plus requireAccountContext, which 53 route files use directly and 14 more through routeHelpers. requireAdminSessionOr403 re-reads users.role. MCP bearer tokens are 'mcp_' plus a sealed SessionData, matched by hash in mcp_tokens, with no user or membership re-check.

**Routes.** Login verifies IMAP and resolves the user from the mailbox, so a shared mailbox's password yields the owner's identity. Signup is invite-gated except in desktop mode; the first user becomes admin, and an admin invite is printed at startup while users is empty. There are no invite CLI scripts. Logout only clears the cookie. switch-account rewrites accountId and the creds in the cookie. Desktop/Tauri uses the same flow without invites, over http://127.0.0.1 with NODE_ENV=production and no keys provisioned.

**Client.** LoginOverlay posts the IMAP password. MailClient treats a 401 under /api/auth/ or with 'Unauthorized' as logout, polls /me, and reads isAdminUser from me.user.role. useAccountController depends on me.accountId and switch-account.

**Tests.** 46 tests in 7 files hand-seal cookies with arbitrary userIds; 5 MCP tests mint tokens directly. No auth or admin route tests exist.

**Under Better Auth:**
- **Credential storage.** Cookie storage mode is dead: DB sessions carry no IMAP creds, so the overlay must go, and team/web mode must use db. Background sync never worked in cookie mode anyway.
- **Active mailbox.** It stops being an authorization input once roles apply. Keep it as a Better Auth session additional field (input:false, written server-side by switch-account), as a pref, or have the client send it. calendar/import and /me (null instead of 403) are the server consumers.
- **User table.** Do not map Better Auth's user onto users: createdAt INTEGER ms and role NOT NULL have no defaults, and Better Auth writes ISO-string dates on SQLite. Use prefixed auth_* tables (avoiding the 'account' vs mailbox 'accounts' collision) with auth_user.id === users.id, and keep users as the Noctua profile/role table.
- **Tests.** A shared helper must seed user, membership, session row and signed cookie, and BETTER_AUTH_SECRET must be set in testSetupEnv.

**Slice 1 (6fee1b8).** Most of it stays: membership roles, prefs, audit, MCP-token revocation, the mergeAccount whitelist, the migration helper and e-mail normalisation. Revert lib/passwords.ts, passwordHash, passwordUpdatedAt, getUserAuthByEmail and updateUserPassword. Revise name, disabledAt and mustChangePassword (each needs a single source of truth or a ban/forced-change decision), plus the insert/delete/profile helpers, the User mapping (hasPassword from the credential account) and the interim signup change.

**IMAP-password first factor.** Better Auth 1.7.12 enforces TOTP only on /sign-in/email, /sign-in/username and /sign-in/phone-number, so a custom IMAP login skips 2FA. The only in-path alternative is a password.verify override hack, and shared-mailbox passwords cannot identify a person. The evidence therefore points to app passwords plus TOTP plus passkeys, with IMAP login at most a one-time bootstrap.

## risks
- Shared bun:sqlite connection: if Better Auth gets the same master `Database` instance as Noctua, its transactions are raw BEGIN/COMMIT on that connection. POST /sign-up/email opens the transaction and then awaits password hashing (a macrotask boundary). Noctua statements running in that gap join Better Auth's transaction, so a sign-up failure rolls them back. A Noctua `db.transaction()` in that gap fails with 'cannot start a transaction within a transaction'. A dedicated second connection (WAL, busy_timeout, foreign_keys) avoids that. However, any Better Auth transaction that holds the write lock across real async I/O (for example a databaseHook doing network I/O) would then make Noctua's synchronous busy_timeout block the event loop and deadlock until timeout. Mitigation: keep sign-up disabled, keep databaseHooks free of network I/O inside transactional flows, and have the spike test both connection setups.
- Mapping Better Auth's `user` onto Noctua's existing `users` table: createdAt is INTEGER ms, but Better Auth writes ISO text and returns the stored integers as raw numbers (mixed types, and ORDER BY createdAt breaks). updatedAt cannot be added by getMigrations on a populated table (UnsafeMigrationError) and must be added by hand as nullable or with a constant default. `role TEXT NOT NULL` without a default must be written by Better Auth (admin plugin or additionalFields with a default). Runtime schema validation (validateSchema, default true) makes every auth request throw SchemaMismatchError if any NOT NULL column without a default is not written by Better Auth. That also applies to any future Noctua column on users or session tables. The alternatives (separate prefixed Better Auth tables, or a fields/additionalFields fieldName remap) must be decided in the spike.
- Name collision and confusion: Better Auth's default table `account` (login credentials) sits next to Noctua's `accounts` (mailboxes) and `user_accounts`. Set explicit modelNames (e.g. auth_session, auth_account, auth_verification, auth_two_factor, auth_passkey) via the options and plugin schema options.
- Passkey sign-in bypasses TOTP by design. The server verifies with requireUserVerification:false, so an authenticator without PIN or biometric counts as a full login. If passkeys are to be a strong single factor, enforce `verification.authenticationInfo.userVerified === true` in passkey({ authentication: { afterVerification } }) and set authenticatorSelection.userVerification:'required'. Set `origin` explicitly; the default trusts the request Origin header.
- Better Auth has no built-in '2FA required' option for all users or per role. Enforcement must be an app-level gate (like the mustChangePassword gate in TEAM-INBOX.md) plus a guard against disabling 2FA.
- freshAge (default 1 day) is measured from session.createdAt. With 7-day or longer sliding sessions, GET /list-sessions and passkey registration fail with 403 SESSION_NOT_FRESH after day one (the docs say list-sessions should not; issue #8175). Noctua needs a 're-authenticate' UX or a larger freshAge.
- Session invalidation differs from the TEAM-INBOX design (passwordUpdatedAt liveness). changePassword revokes other sessions only with body.revokeOtherSessions:true. resetPassword revokes only with revokeSessionsOnPasswordReset:true. Admin set-user-password never revokes. Bans are checked only at session creation. With cookieCache enabled, revoked sessions stay valid up to maxAge. Keep cookieCache off and call revokeUserSessions explicitly in admin flows.
- Admin plugin defaults: the 'admin' role can impersonate users (POST /admin/impersonate-user creates a session for the target). Disable it via disabledPaths or custom access-control roles. Noctua's disabledAt concept has no native equivalent: map it to banned/banExpires, or block it in databaseHooks.session.create.before plus deleteUserSessions.
- IMAP-as-first-factor via a custom password.verify (option A) is global. /change-password then replaces the 'imap:' marker with an app password, admin set-user-password overwrites it, and 2FA enable/disable password prompts hit IMAP. An IMAP outage or slowness blocks login, so keep a passkey or app-password fallback. Option B (custom /sign-in/imap plus reuse of twoFactor's hooks.after[0].handler) depends on internal plugin structure and on the twoFactor path matcher. Both need a regression test asserting twoFactorRedirect and no session cookie for 2FA-enabled users.
- Rate limiting: in-memory, process-local and enabled only when NODE_ENV=production. The client IP comes from x-forwarded-for, single value only, unless trustedProxies is set; otherwise all users share one bucket (3 sign-ins per 10 s for the whole household). Limits never apply to auth.api.* calls, so any Noctua route wrapping auth.api sign-in must rate-limit itself. Configure advanced.ipAddress for the TLS proxy.
- baseURL, cookies and secrets: if BETTER_AUTH_URL or baseURL is missing, the base URL comes from the request Host header. Secure cookies depend on an https baseURL or NODE_ENV=production. Changing the cookie name logs everyone out at cutover. proxy.ts getSessionCookie needs the same cookiePrefix. BETTER_AUTH_SECRET must be at least 32 random chars, and BETTER_AUTH_SECRETS supports rotation. Session tokens are stored in plaintext in the session table, so DB read access means session hijack.
- Test environment differences: under bun test (NODE_ENV=test) the origin/CSRF checks, rate limiting and secret validation are off by default, so tests can miss production behaviour unless advanced.disableOriginCheck:false is set. better-auth/test getTestInstance imports vitest and node:sqlite and does not fit bun test.
- TOTP uses SHA-1, accepts ±30 s and has no replay protection within the window. Backup codes and secrets are encrypted with BETTER_AUTH_SECRET, so losing or rotating the secret without the secrets[] envelope breaks existing 2FA.
- Default password policy (min 8, max 128, scrypt) differs from Noctua's 10..256 argon2id. Set min/maxPasswordLength and custom hash/verify (Bun.password). The default scrypt verify throws on non-scrypt hashes.
- Version churn and supply chain: 5 releases in the week before 2026-10-20, 1.8.0 in beta, about 40 advisories across 2025–2026 (mostly OAuth, SSO and SCIM plugins Noctua will not use), plus about 10 transitive packages including unused DB adapters. Pin exact versions (better-auth, @better-auth/passkey, core and kysely-adapter in lockstep), watch advisories, and only enable the plugins actually needed.
- Better Auth endpoints accept only application/json. Noctua's own non-Better-Auth POST routes do not inherit Better Auth's CSRF/Origin check and keep needing their own protection.
- Peer and type friction: zod ^4.5.4 is required (Noctua ^4.3.6). Core .d.mts imports bun:sqlite and node:sqlite types (fine with skipLibCheck:true). The `casing` database option is declared but not implemented by the kysely adapter.

## summary
Better Auth 1.7.12 fits Noctua's stack, and an IMAP password as first factor plus TOTP works without forking any plugin. All findings come from the published tarballs, which were unpacked read-only (never executed) to /tmp/tmp.LnkmIQSf9H/x/ (better-auth, @better-auth/core, kysely-adapter, passkey, telemetry, api-key, mcp, oauth-provider, utils, better-call, the `auth` CLI). They were cross-checked against the docs and the GitHub advisories, releases and issues. No project files were modified.

Stack fit:
- **Database:** a bun:sqlite `Database` instance is detected automatically (via its `fileControl` method) and runs on an internal Bun dialect with transactions on. In SQLite, dates are stored as ISO text and booleans as 0/1. IDs are strings, and `generateId` can produce UUIDs to match Noctua's ids.
- **Migrations:** `getMigrations().runMigrations()` from `better-auth/db/migration`, or `bunx --bun auth migrate`. They only create tables, add columns and add indexes.
- **Schema check:** runtime schema validation is on by default. Every auth request fails if any NOT NULL column without a default exists that Better Auth never writes.
- **Next.js 16:** mount `toNextJsHandler(auth)` at `app/api/auth/[...all]`. The default basePath `/api/auth` coexists with Noctua's static `/api/auth/*` routes. Cookies look like `__Secure-better-auth.session_token`, and POSTs that carry a cookie get a built-in Origin check against trustedOrigins.
- **Telemetry:** off by default, and no endpoint is hard-coded in 1.7.12. Setting `BETTER_AUTH_TELEMETRY=0` explicitly is still sensible.

Passkeys and TOTP:
- **Passkeys:** `@better-auth/passkey` covers registration, sign-in, conditional UI and passkey-only accounts. Passkey sign-in skips TOTP and does not require user verification on the authenticator.
- **2FA plugin:** offers TOTP, optional OTP by email, backup codes, trusted devices for 30 days and account lockout. It has no built-in "2FA required" option for all users or per role, so that must be an app-level gate.

Can the IMAP password be the first factor?
- **Where 2FA hooks in:** the 2FA plugin intercepts sign-in only through an after-hook whose matcher is exactly `/sign-in/email`, `/sign-in/username` or `/sign-in/phone-number`. A custom path is not covered by it.
- **Option A, least code:** keep `/sign-in/email` and plug in a dispatching `emailAndPassword.password.verify`. If the stored credential is a marker such as `imap:<mailboxId>`, it does an IMAP LOGIN; otherwise it checks the argon2id hash with `Bun.password`. 2FA, rate limits and enumeration protection then work as normal.
- **Option B:** a small plugin with its own `createAuthEndpoint('/sign-in/imap')` that calls `internalAdapter.createSession` and `setSessionCookie`. Its after-hook either reuses the 2FA plugin's exported `hooks.after[0].handler` or copies its roughly 40-line challenge logic (two verification rows plus a signed `two_factor` cookie).
- **Either way:** add a regression test that a 2FA-enabled user gets `twoFactorRedirect` and no session cookie (the lesson from advisory GHSA-xg6x-h9c9-2m83).

Advisories: none of the 2025–2026 advisories affects 1.7.12. The one exception is the organization-plugin invitation issue (GHSA-fmh4-wcc4-5jm3), and Noctua won't use that plugin. Release cadence is very high (1.7.8–1.7.12 in one week, 1.8.0 in beta), so pin exact versions.

Main project risks:
- **Shared SQLite connection:** if Better Auth gets Noctua's master `Database` instance, sign-up opens a transaction and then waits on password hashing. Noctua statements in that gap end up inside Better Auth's transaction. A separate connection avoids that but has its own lock-wait hazard. The spike must test both.
- **Reusing the `users` table:** `createdAt` is an INTEGER in milliseconds while Better Auth writes ISO text. `updatedAt` cannot be auto-added to a populated table. `role` is NOT NULL without a default, so Better Auth must write it.
- **Table names:** Better Auth's `account` would sit next to Noctua's `accounts` (mailboxes). Explicit model names avoid the confusion.
- **freshAge:** the default 1 day is measured from session creation, so after day one listing sessions and adding a passkey fail with 403 SESSION_NOT_FRESH.
- **Session revocation:** admin password reset does not revoke sessions. Password change and reset revoke them only when opted in. Bans are checked only when a session is created.
- **Impersonation:** on by default for the `admin` role.
- **Rate limiting:** only active with NODE_ENV=production, keyed on a single-value `x-forwarded-for`, and not applied to server-side `auth.api.*` calls.
- **Tests:** NODE_ENV=test turns off the Origin/CSRF checks and rate limiting. `better-auth/test` needs vitest, so use the `testUtils` plugin with an in-memory bun:sqlite database instead.
